# Package catalog qualification

A gateway-only SDK declaration has no compiled business owner. It cannot create a
valid empty routing catalog. A fresh SDK package qualification may explicitly add
the released Tenants owner with Builds `test --with-owner tenants`. The SDK's
production declaration and native test facts stay unchanged. Selection preserves
every declared dependency; it does not remove Memories from a default or domain
composition that already requires it.

Platform admits only the following additive package profile:

- A Development run on Linux/x64, owned by a fresh EventStore package test.
- The canonical additional owner set is exactly `tenants`.
- The complete server closure is EventStore gateway, Tenants domain and Tenants API.
- The Builds catalog selects exactly EventStore `4.0.4` and Tenants `7.0.0`.
- Released declarations retain their existing authenticated source commits and
  snapshot hashes. Supplied declarations must still match a freshly authenticated
  closure and the measured published snapshot bytes.

The key-bearing runner entry point verifies the purpose-bound owner request and
creates a private in-memory proof. Ordinary `Compose` options cannot provide that
proof through serialized fields. Admission rechecks the actual source mapping,
Platform root, environment, declaration paths, selected suite and plan metadata
before image probes or resource allocation. Candidate reuse and attachments remain
unsupported for expanded-owner qualification.

The loaded SDK and Tenants Contracts files must match the measured signed public
packages. The reader verifies all four SDK dependencies plus Tenants Contracts and
Server before reading owner attributes or invoking adapter factories. Version
strings alone do not grant capability. Unknown profiles, foreign owners and changed
artifact bytes refuse before catalog output. These package DLLs remain distinct
from the image owner DLLs; image binaries are never installed into a NuGet cache.

Tenants images retain the released `7.0.0` tags and are pinned to these observed
Linux/amd64 manifests:

| Server | Immutable manifest digest |
| --- | --- |
| Tenants domain | `sha256:2f4ab155bc4d33e4b16f1bc8995c45de83503bd8ad99d2c7e46ebbef382b6c42` |
| Tenants API | `sha256:2969ad3f75b154566567dbd6a8f55dd8a64364cbec6fed96398e921379dde9b6` |

Both official image configurations identify source
`1b2c71b0e3cc5b16745f87aa7f1bc2c0ac8ffc27`. Their actual host assemblies contain
the required domain/generated REST catalog registration and receiver calls. The
image Contracts/Server DLLs have different bytes and MVIDs from the signed NuGet
DLLs. A bounded compiled-reader comparison produced identical canonical catalogs
for those two owner inputs; that observation is compatibility evidence, not a
claim that their binaries are identical or that every runtime request is proven.

Memories `3.0.18` remains refused. Its ordinary domain image lacks the required
EventStoreExtensions artifact, and the retained publication evidence does not bind
the observed image digests to a source revision. Its package adapter compilation
alone does not establish image or runtime eligibility. Future SDK or owner versions
require new finite artifact and runtime qualification.

The Builds seed must independently compile its technical receiver against the
actual resolved public Gateway `4.0.4` package. A Builds release containing the
owner-selection and seed changes must be genuinely published and bound in the
Platform tuple before consumer adoption. Local source assemblies or a fabricated
tag cannot substitute for that publication.

Component tests, signature checks, compiled-owner comparisons and reader refusal
controls are supporting evidence. Accepted package execution still requires the
normal published tool/source bindings and a real package run. The 600-second
startup bound, all health checks, writer-protocol cutover condition, source/byte
guards and exact-run cleanup remain mandatory. No package runtime or Works Story
4.9 acceptance follows from this preparation alone.
