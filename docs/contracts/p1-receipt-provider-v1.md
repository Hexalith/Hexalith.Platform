# P1 receipt provider v1 — offline contract

**State:** selected offline encoding and verification contract for the Memories PG2/C1 P1 decision packet of 2026-10-09. This document, `P1BootstrapVerifier`, and `P1ReceiptVerifier` establish no operationally enrolled issuer, key, authenticated target, grant, custody service, status service, or accepting C1 path. `Hexalith.Platform` owns the generic provider contract; Jérôme Piquot is the selected technical maintainer. Security owns operational adoption. The existing GitHub review-observation protocol remains separate and authoritative only for selected review decisions.

## Root-pinned bootstrap v1

An operator must obtain the root P-256 DER SPKI, its lowercase SHA-256 fingerprint, the exact bootstrap payload SHA-256 digest and revision, issuer, audience, receipt and status key fingerprints, retrieval and status origins, and principal-mapping revision through an **independent authenticated trust channel**. The receipt issuer, its retrieval/status responses, a repository fixture, and the bootstrap itself cannot appoint or replace that pin. The API accepts these facts as `P1BootstrapPin`; it cannot prove how the caller acquired them. Security must adopt and retain the root identity and exact revision through an authenticated immutable operator record before any operational enrollment. A successful fixture verification is an offline observation only.

The bootstrap signed payload starts with ASCII `HX-P1B/1\n` (`48 58 2d 50 31 42 2f 31 0a`). Append the following 12 fields in order, each as a four-byte unsigned big-endian byte length followed by exact UTF-8 bytes. The total payload is at most 1 MiB. There is no field count, BOM, separator, padding, trailing byte, JSON form, or Unicode normalization. The exact payload bytes are signed with `ECDSA-P256-SHA256-P1363-v1` using the separately pinned root key; the detached signature is exactly 64 bytes. DER SPKIs are lowercase hexadecimal text in fields 7 and 9. Fingerprints and the payload digest are lowercase 64-character SHA-256 hex. Times use UTC `yyyy-MM-ddTHH:mm:ss.fffZ` without rounding; encoding rejects non-UTC or submillisecond instants. Expiry is exclusive.

| Position | Bootstrap field |
| --- | --- |
| 1–6 | `revision`, `issuer`, `audience`, `retrievalOrigin`, `statusOrigin`, `principalMappingRevision` |
| 7–10 | `receiptPublicKeySpkiHex`, `receiptKeyFingerprint`, `statusPublicKeySpkiHex`, `statusKeyFingerprint` |
| 11–12 | `effectiveAtUtc`, `expiresAtUtc` |

The verifier recomputes the payload digest, parses and re-encodes canonical bytes, checks every pinned scope field, validates each P-256 SPKI and fingerprint, requires three distinct root/receipt/status keys, verifies the root signature, and requires `effectiveAtUtc <= authenticatedNowUtc < expiresAtUtc`. `NO_*` denial values, missing or malformed fields, non-HTTPS or non-origin URLs, wrong root, substituted bytes, expired revisions, and mismatched pins refuse. It creates `P1AuthenticatedEnrollment` only after those checks and copies the verified key bytes. `P1ReceiptVerifier` accepts that type; a caller-created `P1ReceiptEnrollment` cannot be passed to it. The bootstrap digest and root fingerprint remain visible on the result for offline audit. The signed principal-mapping **revision** does not implement, authenticate, or query the map itself.

No network call, root inventory, live status query, trusted clock acquisition, issuer deployment, or operator trust-channel validation is included in this pure verifier. The caller must supply the authenticated UTC instant, exact retained bootstrap and independently obtained pin. Root withdrawal and rotation require a current independently authenticated operator inventory; the bootstrap signature alone cannot prove that the root remains trusted. Do not turn an offline `true` result into an I3 grant.

## Signed objects

There are two domain-separated payloads: receipt magic bytes `48 58 2d 50 31 52 2f 31 0a` (`HX-P1R/1\n`) and status magic bytes `48 58 2d 50 31 53 2f 31 0a` (`HX-P1S/1\n`). Append each field below in the listed order as a four-byte **unsigned big-endian** UTF-8 byte length followed by exactly that many bytes. No field count, BOM, separators, padding, trailing bytes, alternate Unicode encoding, or JSON form is allowed. All strings are case-sensitive; IDs and SHA-256 digests are exactly 64 lowercase hexadecimal characters. Times are UTC `yyyy-MM-ddTHH:mm:ss.fffZ` without rounding; encoding rejects non-UTC or submillisecond instants. Decimal lengths have no leading zero except zero itself. The signed input is **the entire payload from magic through the final field**, without a hash preamble or base64 transformation.

The only signature suite is `ECDSA-P256-SHA256-P1363-v1`: ECDSA over SHA-256 of the signed input, using NIST P-256, with the fixed 64-byte `r || s` IEEE P1363 signature. The detached signature is not a credential. The verification key is the exact DER SubjectPublicKeyInfo (SPKI); its lowercase SHA-256 digest is the key fingerprint. Receipt and status keys have distinct purposes and must have different SPKI bytes. An issuer does not choose a new key through a receipt or response header.

| Receipt field positions | Semantics |
| --- | --- |
| 1–6 | `receiptId`, `issuer`, `keyFingerprint`, `audience`, `kind`, `action` |
| 7–10 | `principal`, `subjectRef`, `subjectSha256`, `subjectLength` |
| 11–16 | `profileSha256`, `workloadSha256`, `tenantId`, `clusterId`, `namespaceUid`, `targetSha256` |
| 17–21 | `sessionId`, `sourceRevision`, `registryRevision`, `policyRevision`, `grantId` |
| 22–25 | `decision`, `reasons`, `issuedAtUtc`, `expiresAtUtc` |

`subjectRef` is exactly `sha256:<subjectSha256>`. The verifier must retrieve or already hold the exact immutable subject bytes, check byte length and digest, and compare **every** claim with a scope independently derived from the approved policy and requested operation. In particular, disposition decision and reason text must match the signed receipt; the signed receipt cannot be used to appoint its own expected scope. Reasons are exact UTF-8 text and may be empty. Every other field is required and nonempty. The fixed `(kind, action)` pairs are `(producer-execution, capture)`, `(grant, grant-session)`, `(target, observe-target)`, and `(custody, retain)`. `decision` is an exact observation or grant outcome bound by the caller's expectation; no outcome string alone authorizes an action. Receipt IDs are issuer-generated 32-byte random values, never selected by a caller.

The versioned subject bytes carry the kind-specific detail: producer command and measured execution; grant gates, principals, actions and separate windows; target API TLS identity, cluster and namespace observations; or custody root, volume, retention and immutable object identity. The issuer must prove those source facts independently before signing. A signed assertion produced after the event is not evidence of historical execution, a target's own label is not cluster authentication, and an archive locator is not immutable custody proof. P3 still has to adopt the exact subject schemas and real sources before use.

| Status field positions | Semantics |
| --- | --- |
| 1–7 | `issuer`, `trustRevision`, `receiptId`, `keyFingerprint`, `grantId`, `sessionId`, `policyRevision` |
| 8–13 | `receiptState`, `keyState`, `grantState`, `policyState`, `sessionState`, `nonce` |
| 14–15 | `observedAtUtc`, `expiresAtUtc` |

The status signer must report a current state for the exact receipt, signing key, grant, policy and session. Each state is exactly `active` for verification; `revoked`, `expired`, `unknown`, an absent field, or any other value refuses. The caller must generate a new 32-byte random lowercase hexadecimal challenge for **each** status request. The status service signs that nonce, so a cached response cannot answer a later request. The pure offline verifier checks the signed nonce against the supplied challenge; the caller remains responsible for generating a fresh challenge and obtaining a new response. A status payload is usable only when its observation is no more than 300 seconds old, its lifetime is positive and at most 300 seconds, and current authenticated time is strictly before its expiry. No offline grace applies.

## Enrollment and principal mapping

An independently authenticated, immutable P1 policy revision must enroll: exact issuer ID; exact HTTPS retrieval origin and status origin; consumer audience; DER SPKI and SHA-256 fingerprint of separate receipt and status P-256 keys; key purpose and validity; effective and exclusive expiry instants; trust revision; approved TLS CA or public-key anchor; client credential issuer and audience; stable credential-to-principal mapping; owner, maintainer, and incident contact. The sole policy decision signer selected by the packet is Jérôme Piquot. The root key and exact bootstrap digest and revision must be established out of band, never supplied by the receipt service, a fixture, or this repository. A policy record must also bind the authorized action, producer identity, target identity, source, session, grant and custody scope. Current values are **`NO_ENROLLED_BOOTSTRAP`, `NO_SUPPORTED_RECEIPT_ISSUER`, `NO_VERIFICATION_KEY`, and `NO_RETRIEVAL_OR_STATUS_ENDPOINT`**.

The issuer authenticates the caller through a verified mTLS client identity whose credential issuer, trust domain, SPIFFE URI SAN and certificate chain are pinned in the enrolled policy. A signed policy mapping translates that exact credential identity to one stable `platform:actor:<ULID>` or `platform:workload:<opaque-id>` principal. An actor mapping also requires the current Platform identity registry entry. Missing, ambiguous, changed or revoked mapping refuses. The receipt principal is an output of that lookup, never a caller-supplied login, Git author, Kubernetes label or self-declared actor. The credential is held by the approved secret boundary and never stored in the receipt, URI, command line, log or subject bytes. No client identity or mapping is enrolled today.

## Retrieval and current status

An enrolled origin must be an exact HTTPS origin without user info, path, query, fragment or trailing slash. The receipt locator is exactly `{retrievalOrigin}/v1/receipts/{receiptId}`. The status locator is exactly `{statusOrigin}/v1/status/{receiptId}?nonce={nonce}`; the nonce is ASCII lowercase hex. Use a fresh authenticated GET with system CA and hostname validation plus the enrolled server trust anchor, and the separately scoped mTLS client identity. Reject redirects, proxies that alter the origin, credentials in URLs, response caching, unknown content type, incomplete reads and responses over 1 MiB. Each request has a 10-second deadline; the whole dependency chain must complete inside 300 seconds from its first request start. Retrieval is by immutable ID; a changed body under one ID refuses and is an incident. Neither URL is a bearer capability.

The response media types are exactly `application/vnd.hexalith.p1-receipt.v1` and `application/vnd.hexalith.p1-status.v1`, with no parameters or case substitution. Each body is a four-byte unsigned big-endian payload length, the exact payload bytes, then the 64-byte detached signature, with no trailing bytes. The approved **total response-body** cap is 1,048,576 bytes. The framing consumes 68 bytes, so a transport payload is at most **1,048,508 bytes** (`4 + payload length + 64 <= 1,048,576`). The separated offline signed-payload verifier can accept a payload up to 1,048,576 bytes; such a payload cannot travel in this response envelope. Empty payloads, unsigned-length overflow, mismatched lengths, truncation, trailing bytes and over-limit bodies refuse.

`P1SignedEnvelopeV1` copies exact decoded payload and signature bytes; `P1ReceiptTransportV1` checks the exact media type and canonical receipt or status payload before returning a document. These are offline byte decoders, not an HTTP adapter. `P1ReceiptVerifier.TryVerify` returns `P1VerifiedReceiptEvidence` only after the root-pinned enrollment, exact claims, subject, nonce-bound current status and both signatures verify. Its lowercase SHA-256 values cover each exact verified receipt/status payload and signature, plus the subject; it also carries subject byte length, verified bootstrap payload digest, retrieval/status URI and request nonce from that verification snapshot. The existing `Verify` boolean has the same refusal behavior. The result contains no caller-owned mutable array and is an **offline observation only**. It is neither a bearer receipt nor proof of operator adoption, actual execution, target identity or custody. A later consumer must compare retained bytes against these digests and independently recheck current authority before use; this API does not perform that consumer action. A locator or self-supplied digest by itself is not authority. Receipt bytes, status bytes, the exact immutable subject, the policy revision and the retrieval observations must be retained under an independently approved custody root.

### Read-only HTTP observation adapter

`P1ReceiptHttpAdapter` composes two exact-origin HTTPS GETs with the offline verifier. A caller must supply a root-verified `P1AuthenticatedEnrollment`, separately scoped `P1ReceiptHttpTrust` for receipt and status origins, exact expected claims, exact subject bytes, and independently authenticated UTC. Each trust binds an exact DNS hostname, a server certificate anchor or actual DER-SPKI SHA-256 pin, the exact mTLS client certificate and private key, its enrolled issuer and any explicit intermediates, and one canonical SPIFFE URI SAN. Production trust also requires the system root chain and offline revocation evidence for both server and client chains. The public trust constructor cannot accept a fixture root. The internal loopback fixture path requires a separate local root, valid chains and DNS hostname checks, and has no operational standing.

The adapter uses Linux 64-bit `CLOCK_BOOTTIME` to advance caller-supplied UTC, includes host suspension in its 10-second GET and 300-second chain limits, and refuses if that clock is unavailable. The caller remains responsible for proving the UTC sample's provenance, same-boot binding and maximum 60-second age. A boottime monitor cancels pending connect, TLS, header and body reads; explicit checks also follow awaited operations and bounded chain validation. Synchronous certificate-chain work has one worker slot per trust and retains that slot until the work actually ends after a timed-out caller stops waiting. TLS chain policy disables certificate downloads and uses offline revocation in production. The adapter depends on current CRL entries in the platform cache, but cannot authenticate who provisioned or refreshed that cache. Security and Operations must attest cache provenance and current validity independently. No online CRL, OCSP or AIA request is permitted.

Raw HTTP/1.1 is used to avoid redirects, proxy configuration, cookie storage and decompression. Both GETs request `Cache-Control: no-store`. A response needs HTTP 200, one exact media type, exactly `Cache-Control: no-store`, one bounded `Content-Length`, a complete body and connection close after the body. Cache indicators, contradictory caching directives, transfer or content encoding, partial content, altered framing and extra bytes refuse. The adapter generates a fresh random 32-byte lowercase hexadecimal status nonce, verifies both signatures and exact scope, and returns copied complete receipt/status frames, subject bytes and `P1VerifiedReceiptEvidence` from the same snapshot. It compares the complete receipt frame, including its signature, against a caller-supplied prior observation and its first accepted frame for that ID. A verified change is an immutable-ID incident; a refused request never seeds history. Local history has no eviction and stops admitting new IDs at **16,777,216 retained frame bytes** or **1,024 IDs**. The frame-byte cap is not a total process-memory bound; the ID cap limits dictionary and string overhead. Durable cross-process history requires independently approved immutable custody. The final boottime/cancellation/expiry check precedes history commit and return, but a narrow unavoidable interval remains before the caller actually receives the result; no atomic real-world return instant is claimed.

The loopback tests do not prove a positive production path. This workspace has no process-isolated system-root and current offline CRL cache fixture for .NET's production `X509ChainTrustMode.System` path; provisioning one by changing the host trust store is outside this local-only test. No host-wide trust store was changed. Public production trust therefore has only explicit refusal evidence here. No live issuer, target, accepting consumer, immutable custody root, trusted time source or operator CRL attestation is enrolled by this adapter.

## Time, rotation and refusal

Use the independently authenticated UTC plus same-boot `CLOCK_BOOTTIME` basis selected by P2. The pure verifier accepts an authenticated UTC input; it does not acquire one. A receipt is valid only from issuance through its **exclusive** expiry, for a positive lifetime no longer than seven days and inside its enrolled key validity. The earliest key, role, grant, session, policy or receipt expiry wins. Re-fetch status at assembly and immediately before downstream use. A new receipt ID is required for each decision or execution; replay across kind, subject, grant, session or target refuses. A later review cannot authenticate an earlier execution.

Planned rotation publishes a new independently signed enrollment revision before use; receipt and status key pairs are purpose-specific. Simultaneously trusted old/new keys may overlap for **at most 24 hours**. An old receipt remains usable only while its exact key, grant, policy, session and receipt all report active under a current authenticated status and enrollment; key withdrawal or revocation has **zero grace**, regardless of its expiry or overlap window. A status-key withdrawal is resolved from the independently authenticated enrollment inventory, not a statement signed by that withdrawn key. Missing current inventory, missing status, stale response, nonce mismatch, unknown principal mapping, untrusted clock, failed subject retrieval, or unavailable issuer refuses. The implementation has a read-only transport adapter but no operator inventory, trusted clock acquisition, custody or operational verifier composition, so it cannot convert an observation into C1 acceptance.
