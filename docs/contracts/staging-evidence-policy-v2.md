Policy identifier `hexalith.platform.staging-evidence-policy.v2`. On 2026-11-19 the Platform Maintainer approved two changes to the release contract. ## Production admission and staging supersession

This section replaces the ordering of successful production admission, staging supersession and a conflicting staging reset in decisions 2, 3 and 5 of v1. A reservation belongs to an existing pending promotion decision. Completed and superseded are still its only terminal states. An explicit Administrator reservation remains a separate signed input with its existing effect.

The Platform promotion evaluator and staging executor must use one durable conditional transition in the existing decision and attempt state. Both must check the authoritative state and its revision when committing. Each uses its own environment lock and current epoch. The record binds the policy, pending decision, exact retained release, accountable signer and authorized action. A production reservation also binds the production attempt and its epoch. The signed decision and attempt encodings identify the authorized writer for each transition. Access to the store alone supplies no write authority. [Release records and writer ownership](../../_bmad-output/planning-artifacts/architecture/architecture-platform-2026-09-27/ARCHITECTURE-SPINE.md#consistency-conventions)

1. **Production admission.** The production evaluator holds the production lock and current epoch, verifies every precondition for the chosen release mode and checks the exact current decision and evidence. Its authorized writer conditionally reserves the pending decision after all checks pass and before the first rollout effect. A queued request, a partially evaluated checklist or a read of a passing result cannot reserve it. Losing the conditional transition to supersession refuses the attempt before mutation.
2. **Staging wins first.** When a staging start or its prerequisite reset would supersede an unreserved candidate A, staging verifies the current decision, absence of a conflicting production reservation and applicability of any signed Administrator reservation. It conditionally claims the supersession once before conflicting work can proceed. A's admission then refuses. Staging applies the reset rule before the later candidate B starts if A's writes are unreadable or their readability is unproven. An explicit Administrator reservation prevents supersession under its existing rule.
3. **Production wins first.** A stays pending and reserved to the exact admitted attempt. Queue staging work that would supersede A or reset the staging state on that basis. Re-evaluate queued work against the authoritative decision, baseline and recovery state before any supersession or reset. Successful production verification and the working-pointer transition complete A exactly once before the baseline change triggers new staging work. B obtains fresh applicable evidence against the new baseline.
4. **Non-working or uncertain production attempt.** The signed non-working terminal outcome releases the matching reservation and leaves A pending, subject to the promotion stop and recovery rules. Another production attempt repeats admission. If the executor disappears or the outcome is uncertain, keep A reserved until authorized fenced takeover or terminal reconciliation establishes the authoritative outcome. Fencing alone is insufficient to declare the attempt working or non-working. A resuming writer must bind its current epoch through the authorized takeover. An old writer cannot release a newer reservation or complete or supersede its decision.
5. **Replay and interruption.** Conditional transitions must be idempotent for the same action and identity and refuse stale epochs or conflicting actions. After a lost acknowledgment, consult the durable committed transition. A partially recorded working outcome or an unavailable authoritative record keeps conflicting work waiting until reconciliation. The working pointer and decision closure must describe the same outcome before a new-baseline trigger proceeds. The staging worker never acquires the production lock.

The earliest pre-write point for a candidate since its last verified reset governs both a same-candidate rerun and a subsequent candidate. Retain that point and its artifacts until its open recovery and reset references allow pruning. Missing proof of baseline readability requires a reset. Completion without successful verification keeps queued attempts blocked. ## Compatible-path rollback witness

This section replaces the unconditional candidate-new command in the compatible-working-baseline row of v1. Story 5.8 compares the exact production working baseline and candidate command catalogs, including command contract identities, and binds the comparison to the releases being rehearsed. The module suite must select the witness from the following cases.

| Verified catalog comparison | Required rehearsal |
| --- | --- |
| The candidate introduces at least one idempotent command | Exercise one such command on the candidate. An existing command cannot satisfy this case. |
| The comparison proves that the candidate introduces none | The module suite names and exercises a representative existing idempotent command on the affected write path. A dependency-only release can qualify this way. |
| Either catalog or a required contract identity is missing, the comparison is inconclusive, or there is no suitable command | Refuse automatic compatibility. Record the missing proof or witness. |

Record both catalog identities, the comparison of their commands and contract identities, the selected command, the affected write path and the candidate-written state and events. Rehearse the prepared AD-15 rollback set with HotReload off and verify that baseline code reads those state and event records after rollback. Failed or absent readback refuses automatic compatibility in both witness cases. Full required E2E, effective module change classification, catalog and key retention and every other applicable AD-15 requirement still apply. An approved retained-data path without valid compatibility needs its own complete E2E and separately rehearsed named recovery. ## Consumer adoption and qualification

Builds and Platform must explicitly adopt the exact committed Platform revision and bytes of v2 together with its pinned base. Record the implementing tool, workflow and evaluator identities, Platform acceptance and the results of qualifying the inherited and changed gates. Every pending decision, attempt and result used under v2 must bind v2. A change of policy requires a new decision and fresh evidence. Refuse missing, unknown or mismatched identifiers, v1 results offered to v2, and v2 results offered to v1. Selecting an unspecified latest version, relabelling results or falling back across versions cannot qualify evidence. Future semantic changes require another immutable version and explicit adoption.

During rollout, enable v2 for a decision only when all writers that could admit it, supersede it or reset its staging state enforce the same ordering rule. A mixed deployment in which a v1 writer can still supersede a reserved v2 decision must refuse v2 activation. Preserve v1 pending decisions and their terminal history under their original rules. Re-intake cannot open a second pending decision for the same retained release.

Stories 4.6 and 4.7 specify writer authority and conditional record updates. Story 5.6 orders staging decisions and attempts, 5.8 supplies the rollback witness, 5.10 qualifies resets, 5.11 evaluates evidence, 6.14 consumes it under the production lock and 6.16 qualifies the working-pointer transition. Platform, Builds, Administrator, EventStore and module owners retain the roles assigned in the base. Policy approval records the design decision. Runtime adoption, integration qualification and release authorization require their own evidence. [Staging consumer handoff](staging-evidence-policy-v1.md#downstream-adoption-and-qualification) · [Story definitions](../../_bmad-output/planning-artifacts/epics.md)

| Qualification case | Required observation |
| --- | --- |
| B's superseding start or prerequisite reset wins while A is pending and unreserved | Exactly one supersession commits. A refuses before mutation. B waits for any required verified reset. |
| A's admission wins while B requests conflicting staging work | B waits. A's success advances the working pointer and completes the decision once. B rechecks its baseline and obtains fresh evidence. A queued request or a failed precondition does not give A this protection. |
| A returns a non-working outcome after admission | The matching reservation is released, A stays pending and the applicable stop and recovery rules hold. A retry repeats all preconditions. Queued staging work reassesses before changing state. |
| A loses its executor or a write acknowledgment during rollout or completion | The reservation survives uncertainty. Only fenced takeover or terminal reconciliation resolves it. Replayed transitions have one effect. Old-epoch writes fail. |
| An inactive or older staging executor can still write under v1 while production proposes a v2 decision | Refuse v2 activation for that decision until only writers enforcing its conditional ordering can affect it. |
| B requests a reset, or A requests a rerun, after A wrote incompatible data | Use the earliest pre-write point since the last verified reset. A later snapshot, a missing point or failed reset verification cannot unblock the attempt. Conflicting work waits for any admission reservation to be resolved. |
| Candidate adds a new idempotent command, or the comparison proves it adds none | The required new or representative existing command exercises the candidate write path. Baseline readback of the actual state and events succeeds after rollback. |
| Catalog comparison is unknown, contract identity is missing, a suitable witness is unavailable, or state or event readback fails | Refuse automatic compatibility in each case. Full E2E alone cannot establish the missing proof. |
| Producer and evaluator bind different policy versions, or the latest required E2E or scan result is stale, incomplete or mismatched | Refuse admission in either release mode. A passing result under an older policy or prior attempt cannot replace the required result. |
