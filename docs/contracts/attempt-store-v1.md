# Attempt store v1

`Hexalith.Platform.AttemptStore` serializes signed attempt, lock, working-pointer and promotion-stop changes using one current head per environment. Callers supply an independently enrolled `RecordTrustPolicy` and signed Builds envelopes. The same policy verifies incoming and stored records used in a transition. Use `ReleaseRecordVersion.V2` explicitly for v2 attempts. Promotion-decision actions always use v2. [Builds record contracts](../../references/Hexalith.Builds/ReleaseRecords.md) · [Staging evidence policy v2](staging-evidence-policy-v2.md)

## Objects and conditional writes

- The mutable head is `environments/{env}/head.json`. Its schema is `hexalith.attempt-store.head.v1`. It carries the revision, prior head's SHA-256 byte digest, epoch, holder, current attempt and working-pointer references, stop state, and receipts for committed transitions. The staging head also carries the v2 decisions.
- Signed envelopes are retained at `environments/{env}/records/{kind}/{recordId}/{digest}.json`. The digest is the Builds SHA-256 signing-content digest. References in the head also bind the exact bytes and schema version where applicable. URI-escape the ID, then escape literal tildes as `%7E` and standalone dot segments as `%2E` or `%2E%2E`. Use `~` followed by the SHA-256 hex of the original UTF-8 ID if its initial URI encoding exceeds 640 characters or the complete escaped object key exceeds 1,024 UTF-8 bytes. A retained release has a copy in each environment that uses it.
- Provision each environment once by calling `InitializeAsync(environment)` to create an empty head at revision and epoch zero with `If-None-Match: *`. It returns `false` if the head already exists. Every transition requires an existing head and reports `head-missing` on confirmed absence. Forbid lifecycle rules and deletion on `environments/*/head.json`, including deletion of versions and creation of delete markers. Head loss is an incident requiring recovery of the original state. Never reinitialize a previously provisioned environment.
- Signed envelopes use create-only PUTs. Every transition replaces the head with `If-Match` against its freshly observed ETag. No mutation of the logical state occurs until the head replacement commits. A losing writer may leave immutable archives without references. Preserve every submitted envelope's exact bytes, including its retained release, so a retry can use the same bytes even when its first write left an unreferenced archive.
- Each head replacement increments the revision and records the previous head's digest. The library rereads and validates state after a conditional conflict. A committed replay returns the original receipt and writes nothing. Replays compare exact submitted bytes. An in-progress attempt replay requires the current epoch. A receipt records a past effect, so callers read the current head for live authority.
- A timeout or other lost acknowledgment requires a strong read. A matching committed receipt and its archived bytes prove the effect, even if later transitions advanced the head revision. The current-epoch check still applies to an in-progress attempt. An advanced head without the receipt triggers revalidation. If the expected ETag still matches or the store cannot read the receipt or archives, it reports `AttemptStoreWriteUncertainException` and callers wait for reconciliation. The S3 adapter disables SDK write retries.
- The current implementation retains receipts in the head and stops accepting transitions if the encoded head exceeds 32 MiB. Retain bucket versions and referenced archives so audit and reconciliation can read them.
- `ReadAttemptAsync` and `ReadDecisionAsync` return `null` when either the head or the requested entry is absent. Use `ReadAsync` for the applicable environment to establish whether the head exists.

## Transitions

| Operation | Required current state and effect |
| --- | --- |
| Acquire | An unheld lock and a new signed in-progress attempt at the next epoch. The record binds the retained release and any active promotion stop. The transition advances epoch once. |
| Revise | The exact current holder and epoch with a valid signed revision. A working or non-working terminal revision releases the lock. Terminal records are immutable. |
| Take over | The current nonterminal holder, a new in-progress successor at the next epoch and an exact, successor-signed terminal revision of the predecessor. The signed links bind both revisions. One head write installs the successor, terminalizes the predecessor and advances epoch. |
| Move latest working | The exact working terminal attempt from this environment and the current epoch, with a signed pointer from the attempt's writer. When a prior pointer exists, the new pointer advances its epoch. The lifecycle must preserve the working attempt's epoch between terminalization and pointer publication by coordinating lock acquisition and takeover. |
| Set a stop | A trusted environment-scoped record naming the next stop revision and its preceding stop. The stop sequence continues across clearances. |
| Clear a stop | An Administrator action naming this environment, the active stop and its revision, and the exact working attempt named by the current pointer. The action must dispose of every outstanding cause. V1 can express at most 128 distinct causes in a clearance. If supplied, a predecessor must name the last committed clearance. Only that environment's active stop changes. |
| Reserve admission | An authorized production evaluator binds the exact in-progress, pre-mutation production attempt at the current production epoch. The action reserves the matching pending decision in the staging head. |
| Reserve as Administrator | A separately signed production-scoped Administrator action protects the pending decision against supersession. |
| Supersede | The initiating staging writer binds the exact current staging attempt and epoch. The decision must still be pending with neither reservation. Callers supply independently verified preparation context for a prerequisite reset, which the store checks against the verified reset and release bindings on each attempt. Consumers must confirm the supersession committed before starting conflicting mutation. |
| Complete or release admission | The production executor binds the current terminal revision, the current production epoch, the admission reservation and the exact revision originally admitted. Completion also binds the committed working pointer. A verified non-working outcome releases the matching admission reservation back to pending. |

The first accepted signed v2 staging attempt supplies the immutable release and decision binding from intake. A fresh decision identity for the same retained release requires all previous decisions for it to be terminal. Their identities and terminal states remain bound. Lifecycle callers own intake, production-baseline eligibility and v2 activation. Production admission and staging supersession both write the staging head. Whichever valid action commits first prevents the other from taking effect. The production head is read during validation and its ETag is checked again immediately before the staging write. This is a read check across two objects. Callers serialize production work through the production lock and reconcile the outcome before advancing its epoch or triggering work on a new baseline. A reservation stays outstanding when the Builds validator cannot establish closure with a takeover successor or a later epoch.

## Failure results

Transitions return `AttemptStoreCommit` or throw. `RecordValidationException.Code` reports a stable failure without echoing record content. Builds verification and transition codes propagate unchanged. `AttemptStoreWriteUncertainException` and provider exceptions such as `AmazonS3Exception` and `IOException` can propagate to the caller.

| Code | Meaning |
| --- | --- |
| `lock-held`, `lock-not-held`, `attempt-missing` | The required holder state or attempt is absent or differs from the request. |
| `stale-epoch`, `invalid-epoch`, `terminal-attempt` | The requested epoch or revision cannot mutate current attempt state. |
| `record-id-conflict`, `record-content-conflict`, `record-reference-mismatch` | An identity, committed action, exact envelope or reference differs from the value already bound. |
| `stop-revision-mismatch`, `stop-not-set`, `working-attempt-mismatch`, `undisposed-stop-cause` | The stop or clearance lacks the current stop state, exact pointer attempt or required cause dispositions. |
| `decision-missing`, `decision-binding-conflict`, `decision-reserved`, `decision-terminal` | The target decision has a different binding or an incompatible current state. |
| `unverified-prerequisite-reset`, `reservation-mismatch` | The supersession lacks prerequisite evidence or closure names a different admission reservation. |
| `invalid-head`, `head-missing`, `record-missing`, `contention` | The store cannot establish valid context or safely finish within the conditional retry bound. |
| `invalid-environment`, `environment-mismatch`, `invalid-record-reference` | The environment is unsupported, the records name different environments or a reference cannot identify an object. |
| `record-too-large`, `invalid-record` | The envelope exceeds the verification size limit or verification failed without a more specific code. |
| `invalid-transition` | The request fails a transition precondition without a more specific code. |
| `head-too-large`, `revision-exhausted` | The head has reached its size or revision limit. |

## Hosting and consumer obligations

The staging instance is hosted in a dedicated Scaleway Object Storage project in `fr-par`, outside the cluster and executor hosts. The bucket has versioning and default 30-day `COMPLIANCE` retention. The staging writer can read its staging keys and use the allowed conditional PUTs. It has no object or version delete permission and no write or read access to the production prefix. The reader identity can read for verification. Keep signing enrollment and private keys independent of object storage credentials, and provide each consumer only the storage access its operation needs. [Hosting and denial evidence](../../_bmad-output/implementation-artifacts/evidence/story-4-7/)

Both heads live in the same bucket under `environments/{env}/`. Production admission, completion and reservation release require a principal that can read the production head and records and conditionally replace the staging head. The same principal needs staging reads and create-only access for staging decision envelopes. The staging writer has no production-prefix read access or authority to perform these production decision actions. Story 6.9 owns provisioning the separate production-decision principal and proving its access boundaries.

Route operational writes through the library so the signed transition checks run. Object Storage enforces the write conditions and retains head versions for audit. Callers must check and fence actual rollout authority before takeover or mutation. Use only confirmed commits for effects that depend on the lock, stop or decision. Preserve outstanding reservations while an outcome is uncertain. Scan evidence, eligibility, issuer integration, executor health, credential vending and v2 adoption remain part of their respective lifecycle gates.

The test assembly runs deterministic in-memory races by default. The hosted suite requires `ATTEMPT_STORE_LIVE_ENDPOINT`, `ATTEMPT_STORE_LIVE_REGION`, `ATTEMPT_STORE_LIVE_BUCKET`, `ATTEMPT_STORE_LIVE_WRITER_ACCESS_KEY`, `ATTEMPT_STORE_LIVE_WRITER_SECRET_KEY`, `ATTEMPT_STORE_LIVE_READER_ACCESS_KEY` and `ATTEMPT_STORE_LIVE_READER_SECRET_KEY`. Supply credentials through the process environment. The live suite initializes a new fixture head under `environments/staging/verification/{runId}/`, verifies that the reader can read the owner-created canary at `environments/production/verification/read-denial-canary.json` and checks that the staging writer is denied a read of that same object. It reports a skip when the configuration is absent.
