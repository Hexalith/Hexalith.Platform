## Proposed decision

Retain the installed OpenBao HMAC binding for its present scope. **Recommend option A as the first feasibility target**, since OpenBao and its transactional storage already exist. Acceptance of this proposal authorizes implementation design for separate DEK custody and the independent surviving authority; it does not establish that the existing cluster/mount meets the lifecycle contract.

| Option | Concrete construction and supported primitive | Required proof before selecting it as the production provider |
| --- | --- | --- |
| A — Purpose-specific OpenBao custody engine | Implement a Platform-owned engine using OpenBao plugin storage transactions. One transaction owns exact tenant target roots, hold pins, original reservation identity, manifest receipt vector and lookup. Its DEK custody class must be isolated from ordinary HMAC/Raft backup recovery and use independently surviving erasure/fencing authority. | Demonstrate native transaction support on the actual selected version/storage, transaction size limits for the bounded 1,000-target manifest, and a key hierarchy that prevents every old snapshot/log/replica from decrypting destroyed roots. Standard storage transactions alone do not supply cryptographic erasure. If isolation requires a separate deployment/storage class, record that explicitly for approval; never silently reuse ordinary Raft snapshots. |
| B — Separate Platform custody implementation | Select a separately operated custody backend with native conditional multi-object transactions and an independently surviving lifecycle authority; implement the six operations in the existing Platform host/library boundary. OpenBao remains the HMAC provider. The backend product, hierarchy, failure domain and operating cost must be named in a follow-up design. | Supply an actual supported transaction API and independently verifiable all-copy erasure/restore behavior before adapters are written. No existing product/installation is claimed by this option; it is a larger selection/provisioning decision. A database transaction over wrapped keys by itself is insufficient. |

OpenBao documents [transactional plugin storage](https://openbao.org/blog/transactions/), which supports investigating A. Its [KV2 API](https://openbao.org/api-docs/secret/kv/kv-v2/) exposes destroy by versions of one secret path. Neither API establishes the required complete production artifact. Looping KV destroys, transit requests, per-key HSM requests, tombstones in the same restored database, or wrapping all roots under a surviving tenant KEK cannot be substituted for all-or-none destruction and old-backup non-revival. No supported turnkey provider satisfying this full contract was established by the inspected sources; both options require the proofs below.

## Exact acceptance criteria

1. **Identity and wrapping:** one original 32-byte DEK for complete `(TenantId, AgentInteractionId, TargetProtectionKeyAlias)`. Source outbox, target event, snapshot and cache use that root. Wrap/unwrap authenticate the complete identity, purpose, lifecycle/store/contract and per-tenant KEK version. Exact wrap retry recovers the original; changed identity conflicts. DEK and KEK bytes stay in bounded owned infrastructure buffers, outside domain records, logs and evidence. Rotation cannot recreate an erased root or require capability renewal.
2. **Pins in the same owner:** `PinDek` and authorized `UnpinDek` retain exact original operation identity and immutable outcomes. A current/unknown hold rejects both per-key and manifest destruction with zero target effects. Race pin/unpin against reservation/destruction at the native transaction boundary; checking a hold and deleting in a later transaction is insufficient.
3. **Atomic manifest:** consume only EventStore's exact original `ConsumptionReserved` receipt and deterministic batch/digest/sorted full target vector. The native transaction validates every root, hold and expected revision, destroys every target or none, and retains the ordered `DeletionTargetReceipt(Target, OriginalBatchId, ReceiptId)` vector. Inject failure at every target and before/at/after commit; no partially destroyed manifest may be reported or left recoverably half-applied. Per-key destruction must not bypass manifest ownership.
4. **Loss and exact outcomes:** response loss, retry, restart, leader failover and unknown commit recover only the original reservation/request. Exact lookup returns the byte-identical original complete vector; changed digest, order, target, tenant or reservation conflicts. An outage is `Unknown/Unavailable`, never `NotStarted`, absence or destruction. Later exact-target requests return authenticated original-batch coverage without allocating another destructive identity.
5. **Isolation and authority:** no cross-tenant alias/key/batch/receipt substitution. Only authenticated infrastructure callers may release keys or consume original reservations. ES256 capability checks, current sole attestation/committed dispatch, private compromise blocks and activation revision comparisons remain independently required at EventStore's owner; custody cannot mint those authorities.
6. **All copies and non-revival:** enumerate replicas, historical KEKs/DEKs, snapshots, backups, WAL/Raft logs, exports, caches, restored clones and recovery/operator paths. Demonstrate loss of decryptability from each old copy after terminal destruction, including a pre-destruction backup restored with old configuration, keys, receipts and owner state. A surviving independent authority must reject rollback and root reissue; a deny flag in the restored system is insufficient. Public verification anchors and immutable outcomes remain available through the complete referenced batch lifetime. Missing copy coverage blocks a terminal irreversible receipt.
7. **Concrete binding and integration:** select the product/version/store identity, custody class, surviving authority and full copy policy, then implement them in Platform and bind EventStore's actual key/binding/atomic provider interfaces. Source/component checks precede narrow integration on the actual backend, with independently read persisted end states. Owner qualification remains a later accepted exact-target run; synthetic components and signed summaries cannot qualify production.
8. **Acceptance boundary:** the complete source, verifier, installed reference-only configuration and public trust pins must exist at accepted canonical targets before Live. Preserve all original operation journals. Do not run phase 0 or OQ-5.4-1, edit the register, enable Agents consumers or declare availability while any prerequisite is missing.

The bounded manifest and sorting/canonicalization come from EventStore Contracts and the Agents EXT-PROTECTION-1 record, including v21/v23 and Owner Qualification Cohorts. No Product hold disposition is chosen here.
