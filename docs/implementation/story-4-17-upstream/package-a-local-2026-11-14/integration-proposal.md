# Package A broker experiment proposal — not executed

Prepared November 14, 2026 for EventStore 3.21 and Platform 4.17. This is a later-execution proposal, not an admitted run or supported runtime. The local component patch and unit tests cannot establish Dapr API error mapping, RabbitMQ fault behavior or persisted effects. Neither parent story closes.

The experiment asks whether a real NACK and revoked-credential error survive through the component and, after supported delivery, through Dapr under the existing deadlines. It also checks that transport cancellation releases the component without allowing delayed work or disrupting a lock holder from a waiting caller. It does not investigate missing-binding rejection or Kafka.

## Component experiment sequence

Use an isolated owned broker, with the above metadata and TLS. A maintainer harness must call the public component Publish method, retain monotonic elapsed time and its exact returned error, and record native broker logs/connection events. This harness remains integration work; the new unit fixtures exercise controlled channels and loopback transports, not RabbitMQ itself.

1. Create the quorum consumer queue and its binding. Publish a unique routed control and verify exactly one persisted effect. Stop the consumer. Apply `rabbitmqctl set_policy qualification-bounded '^qualification-consumer-qualification\.backpressure$' '{"overflow":"reject-publish","max-length":4}' --apply-to queues`. Capture `rabbitmqctl list_queues name policy effective_policy_definition --formatter=json` and assert the effective policy on exactly `qualification-consumer-qualification.backpressure` before pressure starts.
2. Publish eight distinct IDs to `qualification.backpressure`, keeping the five-second request timeout and 3000 ms component outbound deadline when testing through Dapr. Capture each request/payload hash, API response, native confirmation, elapsed time and final error. At least one rejected publication must retain exactly `did not receive confirmation of publishing`. Confirmed retries may succeed; do not count a generic cancellation or socket failure as that rejection.
3. Pause the broker only for a distinct uniquely identified cancellation request. Issue it with the existing one-second client timeout; unpause in a finally/cleanup path. Preserve synthetic 599 as a client transport observation and verify measured elapsed and receipt wall-clock consistency within ten seconds. A faster component cancellation can change what the client observes; record any resulting failure of the unchanged 599 predicate rather than adjusting the request or predicate.
4. Restart the consumer. Reconcile all eight IDs plus the cancellation ID by persisted receipts and effects within ten seconds. Every HTTP-acknowledged ID must be present. Record rejected and uncertain IDs separately, including any late effects; a non-success response does not assert non-delivery. Remove the owned pressure policy during cleanup.
5. Repeat with gates placing cancellation during native exchange declaration, a blocked socket write, confirmation, reconnect setup/confirmation initialization and TLS/AMQP handshake. Start concurrent public Publish callers with independent deadlines behind a stalled holder. Assert waiters return non-success by their deadlines, issue no later publication after release, and do not abort the holder. Then cancel the holder and confirm recovery on a fresh connection generation. Before the abort, deliver a separate uniquely identified message to a consumer without acknowledging it. After transport cancellation and reconnect, prove that subscriptions resume, that unacknowledged ID is redelivered (receipt count at least two, effect count exactly one), and that no acknowledged ID is missing within the unchanged ten-second recovery/readback window. Retain each channel/connection generation and subscription restart receipt because an active transport abort closes the shared connection. These real-broker recovery assertions remain unexecuted integration gaps, even when unit transport tests pass.
6. With the old publisher still alive, create `qualification-v2`, publish its new secret generation, controlled-restart the consumer/new publisher and verify exactly one new-generation effect. Delete old user `qualification`, capture `list_users --formatter=json`, then publish a unique stale ID through the identified old endpoint with the five-second timeout. Capture broker connection close and reconnect refusal separately, actual principal, native error and API response; observe stale effects for three seconds. Require an attributable `Exception (403).*ACCESS_REFUSED` and zero stale effects for the unchanged live-session predicate.
7. Use a separate fresh old-generation connection attempt as a cold control. Preserve its actual native authentication/startup failure. It does not replace step 6. Also test restored broker availability with an independent positive publication and ID readback.

The pinned AMQP library can map authentication-handshake failures to `Exception (403) Reason: "username or password not allowed"`, without `ACCESS_REFUSED`. Preserve that real result verbatim. It fails the current live-session denial predicate if no qualifying attributable denial is captured. A cancellation-induced handshake error is cancellation, not evidence of revoked credentials. If the library cannot retain the broker's actual denial, record the separate upstream/library gap; do not manufacture the missing marker.

The pinned SDK also sends its channel/connection close acknowledgement before publishing the close notification to the component. If that acknowledgement write stalls, a canceled Publish can terminate while the decoded broker reason is still unavailable through the SDK. The retained protocol-peer boundary checks exercise this ordering; it remains an observation/integration limit. Preserve a native reason once observable, but retain cancellation uncertainty when it is not. A broker frame summarized after the response cannot retroactively turn a generic deadline into the accepted API denial. The real-broker experiment must capture this ordering as well as authentication-handshake mapping.
