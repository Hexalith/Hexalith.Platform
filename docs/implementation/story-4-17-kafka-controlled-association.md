## Construction being tested

Keep the actual old publisher running across credential rotation. Before its stale HTTP
publish, establish that earlier work cannot generate an unrelated Produce in the attribution
window; then account for every request and retry generated by the stale operation. A broker
connection/correlation ID identifies a request, but does not by itself identify its HTTP input.

The necessary invariant for this empty-other-work construction is:

1. For the exact old process and producer generation, enumerate every earlier publish
   invocation, including Dapr retries detached by timeouts. Before the stale publish, retain
   completion evidence covering all their component calls, queued messages, retry batches and
   outstanding broker requests. An uncertain transport outcome cannot be treated as absence.
2. During the attribution interval, admit only the one stale HTTP input to that publisher,
   while enumerating its entire Produce request set, including batching, retries and connection
   changes. No earlier invocation or unaccounted caller may contribute a request attributed to it.
3. Bind those requests to the authenticated old credential/process and the actual authorization
   decisions. Preserve the separate new-generation effect and bounded stale-effect readback.

This is a required evidence condition, not a proven property or an implemented verifier.
An alternative design that directly distinguishes HTTP inputs could avoid the empty-work
construction, but that discriminator is still absent from the admitted observations.

## What the paths actually establish

The EventStore [`run_broker` loop](https://github.com/Hexalith/Hexalith.EventStore/blob/51dd68b86a690ffe9e11c565dccec49b2d401a94/tools/qualify-dapr-brokers.py#L654-L681)
creates a publisher and normally reuses it across scenarios. Rotation is tenth in the exact
[scenario order](https://github.com/Hexalith/Hexalith.EventStore/blob/51dd68b86a690ffe9e11c565dccec49b2d401a94/tools/dapr_broker_qualification.py#L13-L17):
earlier calls include restart, retention and duplicate-delivery work. Pressure is eleventh;
pressure timeouts are not prior work for this rotation. On a scenario exception,
[`recover`](https://github.com/Hexalith/Hexalith.EventStore/blob/51dd68b86a690ffe9e11c565dccec49b2d401a94/tools/qualify-dapr-brokers.py#L310-L320)
replaces publisher and consumer. Any eventual proof must follow the actual process lifetime,
rather than assume one uninterrupted publisher for every capture.

[`request`](https://github.com/Hexalith/Hexalith.EventStore/blob/51dd68b86a690ffe9e11c565dccec49b2d401a94/tools/qualify-dapr-brokers.py#L154-L176)
retains HTTP input/status and elapsed time;
[`publish`](https://github.com/Hexalith/Hexalith.EventStore/blob/51dd68b86a690ffe9e11c565dccec49b2d401a94/tools/qualify-dapr-brokers.py#L590-L595)
supplies its five-second default, forwarded to request. The
[stale call](https://github.com/Hexalith/Hexalith.EventStore/blob/51dd68b86a690ffe9e11c565dccec49b2d401a94/tools/qualify-dapr-brokers.py#L814-L831)
uses that default. A synthetic 599 records client uncertainty, not component completion.
The [rendered resiliency](https://github.com/Hexalith/Hexalith.EventStore/blob/51dd68b86a690ffe9e11c565dccec49b2d401a94/tools/qualify-dapr-brokers.py#L527-L536)
gives Kafka a three-second outbound timeout and two retries separated by 200 ms;
[candidate-02 configuration](story-4-17-broker-candidate-02.json) does not override them.

Dapr's [publish wrapper](https://github.com/dapr/dapr/blob/cfb5ee090dda7cfc26145c7703605d831350aa2a/pkg/runtime/pubsub/publisher/publisher.go#L72-L85)
invokes the component through its outbound resiliency runner. The
[runner](https://github.com/dapr/dapr/blob/cfb5ee090dda7cfc26145c7703605d831350aa2a/pkg/resiliency/policy.go#L219-L277)
starts an operation goroutine and can return on the attempt deadline without joining it;
its [retry loop](https://github.com/dapr/dapr/blob/cfb5ee090dda7cfc26145c7703605d831350aa2a/pkg/resiliency/policy.go#L321-L343)
can invoke the operation again. The component ignores the supplied context and waits for
Sarama. **Source inference:** an earlier invocation may outlive its timeout; a later successful
attempt/HTTP response does not join every detached invocation. This is a permitted source path,
not evidence that it occurred in any historical capture.

Sarama [SendMessage](https://github.com/IBM/sarama/blob/8f58ebdcefa5381716d29605b4415fe9f1d59cc1/sync_producer.go#L128-L140)
enqueues a message and waits on that message's result channel. It establishes message-local
completion. The [batch retry path](https://github.com/IBM/sarama/blob/8f58ebdcefa5381716d29605b4415fe9f1d59cc1/async_producer.go#L1468-L1568)
retains messages, backs off and resubmits; transport failure can abandon a connection and retry.
Thus one HTTP input need not correspond to one wire request or one connection. Internal
in-flight accounting is not an exported harness receipt for all Dapr invocations.

The inspected SyncProducer interface exposes no nonclosing Flush barrier. Its
[Close](https://github.com/IBM/sarama/blob/8f58ebdcefa5381716d29605b4415fe9f1d59cc1/sync_producer.go#L187-L191)
starts shutdown; the [underlying shutdown](https://github.com/IBM/sarama/blob/8f58ebdcefa5381716d29605b4415fe9f1d59cc1/async_producer.go#L1647-L1667)
waits for internal in-flight work and closes producer channels. In this construction,
[NewAsyncProducerFromClient](https://github.com/IBM/sarama/blob/8f58ebdcefa5381716d29605b4415fe9f1d59cc1/async_producer.go#L298-L303)
wraps the caller-supplied client in a no-op closer. The component's
[clientOwningSyncProducer.Close](https://github.com/dapr/components-contrib/blob/1d331c389f11baaa1d664022b6b6c2f59811ce11/common/component/kafka/producer.go#L118-L161)
therefore closes the real client separately after the synchronous producer closes. That is
teardown, not an available nonclosing Dapr publish barrier, and does not independently prove
the outcome of uncertain broker requests. Recreating the producer or substituting a cold publisher cannot
establish the required same-live-publisher observation.

## Refusal and next dependency

| Proposed shortcut | Why it cannot establish this invariant |
| --- | --- |
| Sequential calls, HTTP 204 or a successful sentinel | Completion is scoped to a particular operation/message, not all detached invocations or other topic queues. |
| Multiply retry counts by timeouts, then sleep | No measured completion join; ignores scheduling, buffering, metadata refresh and uncertain broker work. |
| Readback finds each earlier ID once | Persisted effects do not enumerate denied, retrying or pending requests; deduplication also hides repeated delivery effects. |
| Match topic, payload size, timestamp or shared client ID | These are not unique HTTP/request associations. A stale input's retry set still needs accounting. |
| Close/recreate the producer before stale publish | No exposed nonclosing barrier; teardown cannot stand in for the required live-session observation. |

**Stop after this source assessment.** Do not implement a causal verifier or run another
logging-only diagnostic from this proposal. No supported completion/discrimination witness
was established. Reopen design only with a concrete source-backed observation that accounts
for all earlier invocations and requests while retaining the live publisher, or a separately
accepted alternative correlation design. More waiting or logger volume alone does not meet that
dependency. This bounded task produces no candidate ready for execution.

The earlier forwarding/process/authenticated-generation mapping and serving-ACL/audit joins
remain required even if HTTP association is later solved. Keep the distinct cold-old-generation
control; it cannot replace live-session denial. Preserve both brokers/all 24 vectors, current
predicates, the five-second stale HTTP timeout, three-second observation window, new effect
exactly once and zero stale effects within that window. Kafka pressure and supported RabbitMQ
delivery dependencies remain unchanged. Exact input admission and an execution decision remain
later steps; no upstream question was sent.
