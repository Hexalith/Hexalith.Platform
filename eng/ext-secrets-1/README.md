==========================

It does not install an owner workload, independent inventory/approval signer, all-copy lifecycle provider, replay registrar credential, qualification executor, enrollment authority, persisted-state observer, or nonrollback restore authority. Retained HMAC verification uses the existing service's accepted timing. Each proof's observation window is checked independently; refreshed observation timestamps do not change stable authority facts. This adapter grants no all-copy erase, approval, replay, direct key delivery or manifest-signing authority.

Only 32-byte canonical base64 HMAC responses in the exact single field are accepted. The Dapr response dictionary is cleared before final public authority/profile reads. Those pure reads have bounded waits, observe late faults without retaining decoded key material, and cannot release a key after the deadline. Decoding happens only after both current public checks succeed; owned bytes are wiped in `finally` and owned snapshots are disposable. Dapr's public client API materializes immutable strings, whose memory cannot be overwritten; one encoded string remains only during the bounded current checks, and is discarded without caching, serialization or logging. This limitation does not establish production memory-erasure qualification.

Provisioning uses the existing OpenBao through Dapr `secretstores.hashicorp.vault`; [Dapr 1.18 OpenBao](https://v1-18.docs.dapr.io/reference/components-reference/supported-secret-stores/openbao/) and [Vault component metadata](https://v1-18.docs.dapr.io/reference/components-reference/supported-secret-stores/hashicorp-vault/) describe the provider-compatible fields. `dapr-openbao.component.proposed.yaml`, `openbao-hmac.policy.proposed.hcl`, and `pod-template-fragments.proposed.yaml` supply proposed component/ACL and actual pod-template fragments with null unknown references. The custody fragment mounts its provider token and CA into Dapr using `dapr.io/volume-mounts`, and wires its separately enrolled API token through `dapr.io/api-token-secret`/`secretKeyRef`. The qualification fragment mounts its own API token at `/var/run/ext-secrets-1/qualification/api-token` and contains no provider token. `pod-credential-mount.proposed.json` is the reference checklist for these fragments. No Secret objects, values or Deployment apply is supplied. The proposed provider token is renewed outside Dapr and rotated only by a separately authorized isolated-pod restart; Dapr reads it once at startup. TLS verification stays enabled. No application token may inherit operator or Memories scope.

Lifecycle-covered DEKs/tenant-key material must use the independently qualified existing separate custody class, excluded from ordinary OpenBao snapshots. OpenBao KV destroy alone cannot prove all-copy destruction, irrecoverable old-backup erasure or nonrollback restore. `tenant-inventory.example.json` and `private-authority-bindings.example.json` enumerate those required provider/copy/journal/restore/authority references, as well as the independently retained public-anchor lifetime. Protocol endpoints and schemas
------------------------------

Only Dapr service invocation is used: `POST http://127.0.0.1:3500/v1.0/invoke/{enrolled-app-id}/method/ext-secrets-1/v1/{operation}`. Operations are enrollment `enroll`, executor `execute`/`lookup`, and independent observer `observe`. A mounted `file:/absolute/path` Dapr API-token credential reference is read transiently for the header; no direct OpenBao/production/SSH fallback or redirect exists. One total monotonic 1–30-second deadline covers credential read/connect/request/headers/body, including continuously trickled input. The caller aborts the connection at that deadline; detached transport work cannot write state or evidence. Responses have a 1 MiB bound, and duplicate JSON properties/nonfinite numbers are rejected. A lost execution result still gets exact original lookup only.

Common request fields are `protocol`, `runId`, `targetCommit`, `isolatedTargetId`, `planSha256`, and deterministic `requestId`. Protocol is `EXT-SECRETS-1.qualification.v1`. Enrollment adds `operation: "enroll"`. Each case adds `caseId`, the independently enrolled `caseTargetId`, `enrolledScope`, and `scenario` containing allowed outcomes, exact required metrics, boundary and four persisted stages. The request ID is SHA-256 of that canonical request before `requestId` is inserted. The client retains `live-plan.json`; `cases.py` is the complete executable client plan and the fixed review matrix independently tests all mandatory cases. Unknown execution results get one bounded exact original lookup; no blind effect retry occurs. Unknown lookup stops that original unless Unknown is the expressly expected isolated failure-injection scenario.

Every response is exactly `{ "payload": { ... }, "signature": "<canonical-base64 64-byte r||s ES256 signature>" }`. The signature covers the canonical ASCII JSON payload, with a P-256 public PEM anchor pinned by the authoritative accepted binding. Every payload adds `identity`, `version`, UTC epoch-second integer `observedAt` and exclusive `validUntil`. Proofs are current within 30 seconds, valid for at most 30 seconds, and checked against the exact independently enrolled identity/version. No `Pass`/`Available` flag or extra unvalidated field is accepted.

Enrollment returns the common binding plus `targetClass: "IsolatedQualification"`, `productionMutationAllowed: false`, `executorIdentity`, `executorVersion`, `observerIdentity`, `observerVersion`, `qualifiedReferencesSha256`, `currentProfileStatus: "Current"`, `currentProfileSha256`, the exact ordered `completeCaseIds`, `caseTargetIds`, and `caseScopes`. The profile hash covers exact runtime `profileReference`, issuer, audience, version, validity and accepted timing. Each scope has `tenantId`, nonempty disjoint `targetIds`, `providerCopyIds`, `logicalId`, `sealId`, `batchId`, `manifestDigest`, `initialAttestationOrdinal`, `initialKeyVersion`, `successorKeyVersion`, `exclusiveExpiry`, `issuer`, `nonceDigest`; all are public references, integers or hashes. Tenant must be enrolled tenant A/B or reserved system; logical ID equals that case's isolated target ID. This is an independent installation guarantee, not an implementation supplied by this client.

Before every new `execute`, the client refreshes the same enrollment request, verifies its fresh signature/exclusive validity and current exact profile, and requires the identical run, authorities, case-target/scope map and original expiries. Only observation validity can advance. The executor still must perform its own current authority check at the actual effect. The refresh grants no capability, delivery, nonce or logical-command renewal. Lookup recovery uses its original request without minting a new effect identity.

After the original is durably published, the client rechecks exclusive enrollment/profile validity immediately before `execute`. Publication can exhaust that window. Such an original remains started in the journal and a later authorized invocation can only use exact lookup; it cannot repeat the effect. An expired installed current profile blocks qualification and lookup pending independently current read authority. This is a current-trust prerequisite, distinct from an expired original delivery envelope or a non-expiring deletion capability. Do not bypass trust, change accepted config pins automatically, renew an original identity/expiry, or delete the original journal to recover.

Executor returns common/case bindings, `outcome` and `resultSha256`. Its exact lookup returns that same immutable original result after loss, restart or restore. `resultSha256` identifies the original content-free outcome/receipt, rather than a fresh attempt or a new release/sign/consume authorization.

Recovery preserves operation-native outcomes: lifecycle Destroyed, delivery Delivered, signing Signed, replay Recorded, consumption Consumed, compromise block ConsumptionBlocked, activation Unconsumed, guard issue Issued, dispatch DeletionBatchDispatchAuthorized, and completion CompletionSealed. Recovery remains in `lookupOnly`, `originalEffects`, `blindRetries` and immutable-original metrics; a wrapper outcome cannot hide native facts. The same delivery instant/expiry, replay identity/retention, exact destroyed-copy vector, signed-versus-issued state, dispatch/reserve/consume order and predecessor/successor activation proofs are checked during recovery. Signed alone has no issue revision or active consumption credential and grants no destruction authority.

Observer returns those executor bindings plus `metrics`, `snapshots`, `linearization`, `proofReferences`, `retainedReceipts`, and `trace`. Metrics are closed integer counters listed per case plus universal zero leakage/foreign effects/revival and exact immutable identity/outcome proof counts. They are insufficient by themselves. The observer must read actual independently authenticated persisted owner state and event/receipt authority, not executor response fixtures or an executor-supplied `passed` assertion.

The replay credential's exact namespace/domain is `system/trusted-envelope-replay`; [current identity derivation](../../../agents/src/Hexalith.Agents.Contracts/TrustedEnvelopeReplay/TrustedEnvelopeReplayIdentity.cs) derives the aggregate from issuer and nonce, excluding the business target tenant. Append only `TrustedEnvelopeFirstSeen` at NoStream; exact lookup recovers loss. The authenticated business target tenant stays in the recorded proof, never in the issuer-wide stream identity.

`snapshots` has exactly `AfterEffect`, `AfterRestart`, `AfterRestore`, `AfterLookup`. Each entry contains `stage`, `originalRequestId`, `originalResultSha256`, `stateSha256`, `authorityRevision`, and `state`. `stateSha256` must equal the canonical state's hash; the four snapshots reproduce the exact original state and receipt. State has closed fields:

```text
requestId outcome receiptId tenantId logicalId sealId batchId manifestDigest
attestationOrdinal keyVersion status targetIds destroyedTargetIds pinnedTargetIds
activeCredentialIds providerCopyIds erasedCopyIds journalRevision deliveredAt
exclusiveExpiry replayNamespace replayTenant nonceDigest firstSeenAt retainUntil
actualIssuedGuardRevision attempts replayIssuer timing rotation attestationHistory
```

Absent optional identity/instant fields are null; collections are ordered unique public SHA-256 identities. Tenant/logical ID/target and provider-copy vectors must match the independently enrolled concrete scope. `receiptId` equals the executor's exact original result digest, and state `status` matches its outcome. State instants use integral UTC epoch milliseconds; ordinal values stay within I-JSON's exact integer range. Delivered requires immutable `deliveredAt < exclusiveExpiry`, including exact-expiry denial. A denial/block cannot retain delivery or destroyed targets. Consumed/Erased/AlreadyDestroyed/Destroyed/CompletionSealed and lifecycle destroy require the complete nonempty enrolled target vector; consumption requires an exact issued state and Dispatch→Reserve→Consume receipts. Recorded and DomainIdempotent replay, including recovered replay, bind exact authenticated target tenant, issuer and nonce digest to the enrolled scope, require `system/trusted-envelope-replay`, and retain `firstSeenAt + 604800000`. OriginalPersisted's independently retained instant fixes the original replay first-seen time; recovery/idempotency cannot reset that clock. Active-credential/destruction counts match actual vectors; pins are a subset of enrolled targets and retainedPins=1 requires at least one enrolled protected target. Restored all-copy targets retain every erased-copy identity.

`timing` has `checkedAt`, `exclusiveExpiry`, `releasedAt`, `authorityChangedAt`, `rotatedAt`, `overlapEndsAt`, with absent instants null. Expiry/actor-revocation cases require actual check/release/expiry or revocation times tied to their typed receipts, including exact before/at/after relations and exclusive expiry. `rotation` is null except required rotation/overlap cases; those include `previousKeyVersion`, `currentKeyVersion`, `rotatedAt`, `oldVerifyUntil`, `publicAnchorId`, `publicAnchorVersion`. Enrolled keys must actually differ. Healthy issuance uses the current key; old-envelope overlap before/at/after must verify the retained initial key while rotation separately proves the distinct current issuance key. HMAC overlap ends at rotatedAt+600000. Non-expiring capability cases and native signing/issue/dispatch/consume/activation/block/completion recovery must retain null state/timing expiry and release fields; the scope's delivery/envelope clock reference does not give a capability an expiry.

Same-batch re-attestation requires exactly two `attestationHistory` entries with `ordinal`, `keyVersion`, `credentialId`, `status`, `sealId`, `batchId`, `manifestDigest`, `blockReceiptId`, `dispatchReceiptId`. The predecessor is RevokedBlocked, the healthy successor is Active at the next ordinal, both preserve enrolled seal/batch/manifest, and only the successor credential is active. Actual Block/Dispatch receipts and key versions must match these retained predecessor/successor proofs.

The three pre-issue `attempts` are checked individually for stable seal/batch/manifest/attestation, exact ordinals 1/2/3, distinct deterministic request IDs, increasing intended guard revisions, exact distinct no-issue proof hashes for the first two terminal ObsoleteUnissued attempts, and a separate actual successful issue revision only on attempt 3. Each no-issue digest must identify its exact retained NoIssue receipt with that attempt's key and intended guard revision. The required order is Sign1→NoIssue1→Sign2→NoIssue2→Sign3→Issue; unrelated, unretained, reused or late proofs cannot authorize a successor. Attempt fields are `sealId`, `batchId`, `manifestDigest`, `attestationOrdinal`, `signingAttemptOrdinal`, `intendedGuardRevision`, `actualIssuedGuardRevision`, `keyVersion`, `requestId`, `outcome`, `noIssueProofSha256`. No expiry, renewal or changed batch is allowed.

`trace` is a bounded ordered vector (4–100 events) with fields `kind`, `position`, `requestId`, `receiptId`, `originalReceiptId`, `tenantId`, `batchId`, `keyVersion`, `guardRevision`, `blockSetRevision`, `occurredAt`, `stateSha256`. Permitted kinds are OriginalPersisted, Effect, Lookup, Restart, Restore, Block, Reserve, Consume, Activate, ActivationBlocked, Dispatch, Hold, Compromise, Complete, Sign, NoIssue, Issue, Expiry, Verify, Release, DenyRelease, ActorRevocation, Destroy, GuardMutation. Each event's original receipt matches retained state; its receipt is in the independent proof references, and its state hash matches the actual snapshot. Observer `retainedReceipts` contains the exact ordered `kind`, `position`, `receiptId`, `keyVersion`, `guardRevision`, `blockSetRevision`, `occurredAt` records independently read from the persisted owner ledger; trace must reproduce those records. This receipt ledger is separate from the unchanged original business state, so earlier snapshots do not need future recovery records. Recovery events specifically bind each stage's original receipt and state hash; OriginalPersisted identifies persistence of the original outcome after effect resolution.

The client checks exact recovery order, same-owner block/reserve winner, no consume after a winning block, replacement-key block-set compare/activation winner, and block→issue→dispatch→activate→reserve→consume re-attestation order. Required activation counts match actual typed Activate receipts; retaining an existing guard credential proves no new activation and does not force every blocked state's credential vector to be empty. Three stale-race signing receipts bind the actual key/intended revision for each attempt; issue binds the final key and actual successful revision. `linearization` is empty except races, with `boundary`, `triggerPosition`, `effectPosition`, `winner`; positions must identify the actual typed Hold/Dispatch, Compromise/Dispatch, GuardMutation/Complete, Block/Reserve, Expiry/Verify or release, and activation receipts. Receipt ordering and actual timing determine the winner. Concurrent activation may win before the second compromise, which must still block the enrolled replacement key before reserve. At least four distinct independently retained receipt/proof SHA-256 references are required. These checks depend on the independently installed observer's actual owner reads, whose implementation remains missing.

Only fully schema-checked signed public proofs are retained. Invalid provider payloads/errors are discarded; failed runs retain the valid original request/outcome/proofs already captured and a sanitized failure record. A full pass permits owner acceptance only for the exact target/run/installed authorities; `dependencyAvailable` remains false because acceptance and register updates belong to the owner.
