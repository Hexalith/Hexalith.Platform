# Hexalith Platform

## Why

**Vision to realize, driven by a pain.** Each Hexalith module wires its own hosting today: domain AppHosts, per-module Dapr plumbing, file-existence source switches. The only root composition is an opt-in Works preview, and no hosted Kubernetes or domain configuration exists. As a result, developers cannot reliably run the whole system, or one module with only its dependencies. CI has no shared real-service environment, and there is no gated, recoverable path to production. Hexalith Platform gives the internal team one solution for development, testing, staging and production. Platform owns shared hosting, composition, promotion and recovery; modules keep their domain behavior. It serves developers, team members using hosted environments (including through McpCli), automated CI workflows, Administrator (the production authority and recovery owner) and a named recovery deputy, who receives every notification and can restore, verify and reopen service when Administrator is unavailable. The designated Kubernetes installation and a shared Keycloak server already exist. The MVP proves the model on seven modules before the rest enroll through the same schema.

Mechanism authority is the adopted [architecture spine](../../planning-artifacts/architecture/architecture-platform-2026-09-27/ARCHITECTURE-SPINE.md) (final, updated 2026-09-28). This spec cites its decisions as AD-1..AD-15 and its sections by name, and re-decides none of them.

## Capabilities

CAP-N maps one-to-one to PRD FR-N. Full testable consequences: [acceptance-criteria.md](acceptance-criteria.md).

- **CAP-1** — Complete local environment
  - **intent:** A developer starts the complete MVP environment locally through Platform to test and debug. It contains EventStore, Tenants, Parties, Folders, Projects, McpCli and Memories plus their supporting components.
  - **success:** All seven modules report module-owned readiness together within the effective startup deadline. The local McpCli client connects and executes enabled modules' agent-eligible operations through CLI and MCP, with no hosted McpCli service (SM-1). AD-1, AD-9, AD-13.
- **CAP-2** — Debug the active module checkout
  - **intent:** A developer runs and debugs a domain module from its own workspace, which includes Platform as a direct submodule, executing the checkout being edited. EventStore, Memories and McpCli are debugged from source in the Platform workspace.
  - **success:** Breakpoints and source changes affect the running code in each domain-module workspace (Tenants, Parties, Folders, Projects), and for EventStore, Memories and McpCli in the Platform workspace. Only the active root's direct `references/` declarations are initialized. Local runs use project references and Debug; CI uses NuGet and Release (SM-2). AD-4.
- **CAP-3** — Developer-defined minimum environment
  - **intent:** A module developer declares the servers the module needs for development and integration testing, and Platform composes exactly that minimum environment as real services.
  - **success:** The Parties workspace runs the active Parties checkout with EventStore, Tenants and Memories as its declaration specifies, and no unrelated domain module (SM-2). AD-1, AD-4.
- **CAP-4** — Real-service integration test environments
  - **intent:** A developer or CI workflow provisions the declared environment and runs integration tests against real services. Tests wait for readiness, data is isolated, and retention and cleanup are limited to what the run owns.
  - **success:** Local Aspire and CI runs pass module-defined checks. CI evidence identifies the candidate revision, expected artifact identities and the artifacts actually loaded. Controlled success, failure, startup-timeout, cancellation, collision, attachment, hold-expiry and withdrawal scenarios show the agreed ownership, retention and cleanup, with leftovers reported, diagnostics preserved and no other environment touched (SM-3). AD-4, AD-5, AD-10.
- **CAP-5** — Isolated tests without Platform
  - **intent:** A module developer runs isolated tests from the module's test project without starting Platform, using lightweight doubles where needed.
  - **success:** Isolated tests pass with no Platform or domain server running. CI runs them before integration tests, and an isolated pass never satisfies integration acceptance (SM-3). AD-5.
- **CAP-6** — Critical-flow staging gate
  - **intent:** Platform promotes a release to production, in either release mode, only after staging E2E tests pass for every enrolled module's critical flows, run against that exact release.
  - **success:** Every promoted release has complete passing staging evidence for that exact release and retained artifacts. Missing, skipped, failed, incomplete, stale or wrong-release results block promotion. Automatic promotion additionally needs G3, compatibility evidence against production's working baseline and a passing shared-infrastructure currency check (SM-5; SM-C1 = 0). AD-2, AD-7, AD-13, AD-15.
- **CAP-7** — Production deployment verification
  - **intent:** Platform verifies that a production deployment reaches readiness and passes module-owned production-safe smoke checks before declaring it working, and detects failure.
  - **success:** Rehearsals fire each failure trigger: rollout not ready within 10 minutes, 60 continuous seconds of unavailability, two consecutive smoke failures, and a missing result. Only a clean verification window yields a working release (SM-5). AD-2, AD-3, AD-7.
- **CAP-8** — Verified recovery to the previous working release
  - **intent:** Platform recovers an eligible failed compatible deployment once to the recorded working application without rewinding data, and controls approved empty, degraded or incompatible attempts through their recorded recovery paths.
  - **success:** A rehearsed automatic rollback restores readiness within 10 minutes and passes the five-minute verification using the restored release's smoke checks, with data intact. Rehearsals also prove retained-data compatibility or named data restore, per-cause promotion stops, admission reconciliation, first-install and failed or unverified paths, and no second automatic attempt. Administrator and the recovery deputy receive GitHub reports; only Administrator approves attempts and clears stops (SM-5; SM-C3 = 0). AD-2, AD-3, AD-15.
- **CAP-9** — Production backup and disaster recovery
  - **intent:** The recovery owner or the recovery deputy restores production onto prepared capacity from recovery points kept outside the primary failure domain, and verifies it before reopening.
  - **success:** An isolated drill proves RPO at most one hour and, for outages beginning within declared response coverage, RTO at most four hours from outage to verified service, including fencing, integrity, smoke, access, admission-revocation and erasure-safe tenant-key checks. Backup cadence, retention, monitoring and GitHub alerts to Administrator and the deputy are verified; post-cut grants are listed for Administrator rather than restored as authority (SM-6). AD-7, AD-12.
- **CAP-10** — Isolated staging and production
  - **intent:** Platform hosts the MVP modules in staging (`hexalith.com`) and production (`tache.ai`) on the designated installation, with separate application data and credentials.
  - **success:** Both environments expose the MVP interfaces. Negative tests from staging users, workloads, credentials, automation and pods reach no production data, secrets, ports, hostnames or administration (SM-4; SM-C2 = 0). AD-6, AD-8.
- **CAP-11** — Explicit production-user access
  - **intent:** Production access requires explicit admission, which only Administrator grants or revokes through an authenticated, auditable action. Staging authorization and recovery authority never confer it.
  - **success:** Staging-only users are denied production data and operations through the API, CLI and MCP. An authorized production user receives exactly their production permissions; admission revocation survives restoration, and reconciliation fails closed on record-chain or two-way membership mismatch (SM-4; SM-C2 = 0). AD-6, AD-14.
- **CAP-12** — Module operations through McpCli
  - **intent:** A user discovers and invokes enabled modules' agent-eligible commands and queries through the McpCli CLI or MCP, in a selected local, staging or production environment and under that environment's permissions.
  - **success:** Operations execute only in the selected environment, through its gateway. Ineligible (UI-only or confirmation-required), disabled-module, mismatched-contract and unauthorized operations are refused, and an empty executable catalog cannot satisfy acceptance (SM-1, SM-4). AD-11, AD-13, AD-14.

## Constraints

- **Spine precedence.** The spine governs mechanism. Where it refines a PRD rule, the spine applies. AD changes go through bmad-architecture, never through this spec. The finalized PRD, addendum and architecture update 4 are synchronized ([sequencing.md](sequencing.md#source-document-alignment)).
- **Ownership.** Platform owns shared hosting, composition, promotion and recovery. Modules own domain behavior, server lists, readiness semantics, public operations, critical flows, smoke suites and authoritative-state inventories. Platform implements no domain behavior and no second orchestration framework (AD-1).
- **Roles.** Only Administrator approves releases, clears promotion stops and grants or revokes production admission. The named recovery deputy receives every notification, holds independent recovery and key access, and may declare a stop, execute documented recovery, verify restoration and restore only the recorded pre-incident ingress state. The deputy cannot approve a release, clear a stop or administer admission; before G2, reopening keeps user ingress closed. Recovery never grants admission or roles (spine Roles, AD-6).
- **Single composition model.** One Platform-owned Aspire model, launched by the Platform tool, composes every environment. No AppHost runs in production. The retained application Helm package is the only staging and production deployment definition (AD-1, AD-2).
- **Platform tool and runner.** Builds' `hexalith-module` is the Platform tool (AD-4) and the runner (AD-10). Platform owns the declaration semantics and lifecycle rules; Builds implements them. Published versions through 4.27.4 and `hexalith.module-manifest.v1` are not Platform-accepted; the Platform declaration ships as the next manifest major (spine Module declaration).
- **Active-root dependencies.** Only the active root repository's direct `references/` declarations are initialized. No recursive or remote submodule updates; nested submodules stay uninitialized, and any initialized by accident are deinitialized. No ancestor, sibling or package fallback. Local builds use project references and Debug; CI/CD uses NuGet packages and Release (AD-4, AD-5).
- **Platform identity.** Every workspace other than Platform that runs the tool, McpCli included, declares `references/Hexalith.Platform`; its submodule commit is the Platform identity, and in the Platform repository the identity is HEAD. Package mode builds the composition from that submodule at a Platform release tag and refuses identity, Builds-catalog or tool-range mismatches; source mode warns. EventStore, Memories and McpCli produce Platform evidence only from the Platform workspace (AD-4).
- **Candidate CI identity.** Candidate evidence binds the declared committed revision and expected content identities to every candidate Release artifact the composition actually loads, including Contracts, server and extension packages, services, tools, packages inside the composed host and run-scoped McpCli. Missing identities, caches or substitutions from another build or revision, uncommitted inputs and labelled baseline-only runs cannot pass candidate acceptance. The shared Platform/Builds candidate-selection, gated-decision and evidence-reuse policy precedes acceptance (AD-4, AD-5).
- **Real services only.** Platform environments run only the configured real services. Test doubles exist only in module-owned isolated tests.
- **Readiness.** Each module defines readiness for its services. A running process is not readiness, and a required service without usable readiness evidence is a configuration error. The default test startup deadline is 10 minutes; only a justified finite override, shown in diagnostics, may change it.
- **Run-owned test environments (AD-10).**
  - Each suite or compatible batch gets a fresh run-owned environment, or fails naming the conflicting run. Explicit attach requires compatible composition, mode, artifact identities, readiness and isolation; hosted attachment fails, and post-owner-finish attachment is refused unless the local environment was retained after failure.
  - The owner outcome records immediately. Accepted attachments hold cleanup only until all end or their finite recorded hold expires. Hold expiry, owner cancellation or explicit stop withdraws affected attached runs; withdrawal is neither pass nor failure and is never integration evidence.
  - Local success cleans after attachment holds. A test or startup failure by the owner or any attached run retains the environment; later cancellation cannot erase that retention. Explicit developer cleanup remains available.
  - CI attachment stays within one job. Job completion or cancellation withdraws attached runs first, then always cleans all owned resources, including after partial provisioning.
  - Cleanup never touches another run or a hosted environment, reports leftovers, and results and diagnostics survive it.
- **Hosting.** The designated Kubernetes installation is `192.168.1.30`, with staging on `hexalith.com` and production on `tache.ai`. Supporting infrastructure may be shared only if application data, credentials and namespaces stay per environment (AD-8).
- **Identity.** The existing shared Keycloak hosts separate staging and production realms. Production admission is membership in the human production-admission group, granted only by Administrator: never by default, by promotion, or by copying staging membership. Synthetic actors use a separate synthetic-admission group limited to the synthetic tenant (AD-6, AD-14; spine Synthetic identities).
- **Same release digests.** Promotion ships the same retained package and image digests that passed staging. Evidence is bound to the exact release, and absent evidence is never a pass (AD-2).
- **Release modes.** *Automatic* needs G3, complete compatibility evidence and the shared-infrastructure currency check. *Administrator-approved* serves pre-G3 releases, SM-5 fault rehearsals before G2, empty or degraded production, and releases without demonstrated safe rollback. Empty means no working baseline; degraded means the last outcome was non-working or an incident, over-bound probe failure or failed health check shows production is not working. Reduced-recovery state is distinct. With retained application data, an approved attempt still needs valid evidence against its recorded baseline or a named data-restore recovery with acceptance checks, maximum duration and a usable post-lock recovery point. Only a first installation with no retained application data uses fresh-install proof. Common gates, lock, provenance, verification and records apply in both modes (RRA Release modes, Empty or degraded production; Production preconditions).
- **Production verification defaults.** Rollout must reach readiness within 10 minutes of deployment start, followed by a five-minute verification window. The deployment fails on 60 continuous seconds of unavailability, two consecutive smoke failures with the second 30 seconds after the first, or a missing result. One failed probe or one restart does not fail it. These defaults must be validated in staging; they are not availability guarantees.
- **Recovery paths.** An eligible compatible failure gets exactly one automatic application rollback: 10 minutes to readiness, then the same five-minute verification; it never cycles through older releases. A baseline re-deploy handles a failed automatic recovery. A named retained-data recovery uses the in-place data-restore form of the Recovery sequence. Replacement-capacity disaster recovery runs that sequence on the recovery executor. Each path becomes the working baseline only after its required verification (RRA Automatic recovery, In-place recovery, Recovery sequence; AD-7).
- **Recovery timing and fencing.** Resume and takeover preserve the attempt's original absolute and phase deadlines and remaining recovery allowance. A new epoch does not authorize mutation until every affected prior-epoch credential is revoked and its authority is fenced or drained; recovery-scope tasks commit only while their invoking epoch is current. Interrupted recovery re-enters through its own recovery-kind path (RRA Attempt ownership, Timing and interruption; Recovery sequence).
- **Promotion stop.** Stops are per environment and each new cause advances a monotonic revision. Production causes include every non-working outcome and recovery entry, failed pre-update health or over-bound probe failure, a recorded incident, a two-way admission/record mismatch, and an Administrator or deputy declaration. Monitoring sets and notifies but never clears. Administrator clearance uses compare-and-set against the observed revision, names every cause resolved or accepted, reviews lost-window handling and confirms admission matches; a later cause wins. An unaccepted continuing cause re-records after clear, while an accepted cause waits until it resolves and recurs (RRA Promotion stop).
- **Release tiers and records.** Every deployed object belongs to exactly one tier (application package, environment layer, shared infrastructure, outside every release) with one version authority. Application rollback touches only the application package. Records are accepted only when signed by their named writer, never by store access (AD-3; spine Release tiers; Binding classes and records).
- **NFR-1 rollback data safety.** Application rollback never rewinds business data, event history, credential rotations, revocations or key generations. Automatic releases must keep schemas and event formats compatible with the previous version. Incompatible releases use the Administrator-approved mode with a planned recovery (AD-3, AD-15).
- **NFR-2 recovery bounds.** RPO at most one hour, continuously. RTO at most four hours for outages beginning within declared response coverage, from outage to verified service, including detection, operator response and capacity. Coverage (time zone, primary and deputy responsibility, maximum acknowledgement time) is published before the first qualifying drill; deputy hours count only after the G2 deputy proof, and the outage clock never pauses. Backups run every 30 minutes, keeping frequent recovery points for seven days and daily points for 30 days, encrypted and outside the primary failure domain with independent access and decryption keys. Monitoring checks at least every 15 minutes and alerts when the newest usable point is over one hour old. Every point and restore covers each referenced non-erased tenant-key generation; current tombstone authority plus known lineage may prove an intentionally erased generation absent, which must never be restored. Unknown lineage or any unexplained missing generation fails closed. These are targets that have not yet been demonstrated (AD-12; RRA Recovery point and freshness, Detection and response).
- **NFR-3 isolation.** Isolation holds at service, data, routing and administration boundaries, including direct requests that bypass UIs and restored copies. It is verified by negative tests from staging users, workloads, credentials, automation identities and pods, plus a positive production-user test and denial after revocation (AD-8, AD-14).
- **Dapr boundary.** Dapr is the runtime infrastructure boundary. Only the named AD-9 exceptions (Memories FalkorDB graph, Memories Redis search/vector, the Memories SET NX preflight row) use provider SDKs. A new exception needs Administrator acceptance recorded in the spine (AD-9).
- **Executor isolation.** Staging, test or PR code never runs where production credentials are or were held. Deployments run on isolated per-environment executors from the private operations repository, whose only writers are the named writers; module-supplied code on an executor runs in a sandbox without job credentials (AD-7).
- **Notifications.** GitHub issues in a private notification repository, assigned to Administrator and mentioning the recovery deputy, are the single accepted notification path. Every deployment-failure, recovery, backup and monitor notification reaches both. Reporting keeps working while the primary environment is down (spine Diagnostics and notification).
- **MCP and CLI surfaces.** McpCli stdio is the only MVP MCP surface, and McpCli executes only agent-eligible operations. Legacy module and technical-module MCP hosts, plug-ins and CLIs, including EventStore Admin.Cli and .Admin.Mcp, are frozen: never enrolled, deployed, routed, mapped in an enrolled host or issued a realm client in any Platform composition, and retired only with the AD-11 evidence. Any new MCP/CLI surface or transport, including McpCli HTTP, needs a Platform AD under AD-14 (AD-11, AD-14).
- **G1.** Production is first deployed with ingress closed, admitting only executor and probe sources, with an empty human production-admission group, on a supported Kubernetes minor, with GitHub delivery working. Before G2, Administrator may temporarily grant one designated synthetic identity, limited to the synthetic tenant, solely for SM-4 positive evidence; its record expires no later than G2 and its revocation is followed by a denial check. This does not open G2 ([sequencing.md](sequencing.md)).
- **G2.** Production users are admitted and ingress opens only after the AD-12 drill passes, including Memories tombstone and key continuity; SM-4 isolation and access checks pass; and recovery access, capacity, deputy alert delivery and response coverage are verified. Admitting the first user is an access-configuration change: SM-4 is re-verified on the live realm with that user before anyone else is admitted. The PRD's "before production use" means G2: SM-4 and SM-6 are its entry evidence.
- **G3.** Automatic promotion is enabled only after the SM-5 rehearsals pass; this is the PRD's "before enabling automatic production promotion". A change to verification, recovery or rollback-set policy suspends it until the affected rehearsals repeat. Before G3, every production release uses the Administrator-approved mode.
- **First shared versions and Owned work gates.** Module adoption epics wait for the First shared versions artifacts they consume, and remaining work lands at its spine Owned work gate. Shared candidate/attachment policy precedes CI evidence; monitor and admission bounds precede G1; reduced-recovery operating policy precedes G2; shared-infrastructure currency policy precedes G3. Each artifact or policy exists and is qualified before the consumer or gate it controls ([sequencing.md](sequencing.md)).
- **Source precedence.** The Platform MVP recovery envelope governs the stricter infrastructure clauses of Folders and Projects without blocking their enrollment. Module behavior, authorization, data-safety and release gates are never waived.
- **Evidence.** Deferring work assigns it; it never turns absent evidence into a pass. These are target requirements. A document marked final does not establish an implemented capability, a passed runtime check or a production qualification.

## Non-goals

- A generic Platform mocking subsystem, fake-service catalogue, or per-service real/fake switches. If a concrete test later needs a substitute service, that case is assessed on its own.
- Standalone module workspaces for EventStore, Memories or McpCli; their source debugging stays in the Platform workspace.
- Rollback triggered by traffic metrics (error rate, latency) in the MVP.
- Automatically reversing business data or event history on rollback, switching releases indefinitely, or automatically handling failures found after the verification window; those are operational incidents.
- An emergency release path that skips the staging gate, including after DR.
- A standby production installation, automatic infrastructure failover, HA or warm standby, multiple regions, broker changes, scaling work or in-transit TLS for every data service without a measured requirement.
- A numeric uptime percentage, latency or throughput targets, 24/7 response, or a cost target.
- MCP and CLI surfaces beyond McpCli stdio and its CLI head: hosted HTTP MCP, McpCli HTTP, Memories.Mcp, Parties.Mcp, FrontComposer MCP, EventStore Admin tools; step-up or confirmation flows through McpCli; system-initiated cross-module operations without a user actor. Each needs an AD first.
- Platform maintaining a central list of critical flows or smoke suites, or its own business implementations of module operations.
- Including servers outside the MVP set (e.g. Agents, ChatBot, Conversations, Timesheets, Works) in MVP acceptance. They stay in longer-term scope and will enroll through the same declaration schema.
- The Projects G-1 durable task engine; the HA, RPO-0 or 15-minute RTO infrastructure guarantees in Folders and Projects documents; a custom orchestration DSL, environment service or per-dependency retry policy.

## Success signal

- A developer debugs Parties from its own workspace against real EventStore, Tenants and Memories. A release that passed staging E2E for that exact release reaches `tache.ai` through G1, G2 and G3. A rehearsed failure rolls back once with data intact, and a drill restores production within a one-hour RPO and, for an outage within declared response coverage, a four-hour RTO.
- Each SM-1..SM-6 demonstration is recorded with release, environment, result and diagnostics, and SM-C1..SM-C4 stay at zero ([success-measures.md](success-measures.md)).
