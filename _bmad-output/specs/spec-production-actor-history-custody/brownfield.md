## Existing backend and recovery evidence

The [October 1 OpenBao proof](../../implementation-artifacts/evidence/epic-4/4-0/20261001t061620z/openbao-proof-summary.json) records the shared three-voter `openbao/hexalith-keys` Raft deployment and isolated recovery of KV paths, canary entries, mounts and policies. Snapshots were retained off-node in Scaleway with 30-day COMPLIANCE object lock and provider-managed encryption. This is historical generic recovery evidence, not a current inventory or an actor-history destruction test.

**Inference from that evidence:** storing purpose keys or lifecycle state in ordinarily restorable OpenBao snapshots can restore old key/state copies. A separate namespace or successful generic restore cannot establish irreversible per-unit expiry. Any proposed OpenBao adapter must prove which keys escape ordinary snapshots, how every earlier key backup becomes unusable and which independent authority prevents rollback. Immutable ciphertext may remain only when no surviving generation can decrypt it; physical deletion at expiry cannot be assumed for locked objects.

The lifecycle document reports unsuccessful Azure vault discovery because an MSAL token was unavailable. No production adapter was selected. This does not establish Azure suitability or require switching providers; Q1/Q2 need an owner-approved, read-only capability investigation.

The input Branch B spec explicitly keeps independent custody, all-copy receipts, nonrollback restore, successor continuation and complete installed P-01–P-10 open. Its historical local test counts are not evidence of availability. The inspected sprint register lists 4.9, 4.15, 6.7 and 8.6 as backlog, and 4.10 as in progress; Story 4.0's generic recovery proof is marked done.
