# Epic 2 Context: Test modules against real services, locally and in CI

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Give developers and CI real-service integration environments owned end to end by the Platform runner (`hexalith-module`): run-scoped resources without collisions, readiness-gated startup, isolated test data, safe explicit attachment with finite holds and withdrawn outcomes, local failure retention for debugging, and disposable CI runs that always clean up with leftover reporting. Isolated tests run first without Platform while package-mode real-service integration blocks CI. The epic also publishes the shared candidate-and-attachment policy, adds a disposable run-owned workload-binding authority, streamlines Platform tuple CI to the current candidate commit, and pins Builds and owner modules by released version with NuGet lock verification. Candidate artifact-identity population follows in Epic 3.

## Requirements & Constraints

- **Real services & test tiers:** Integration tests run against real declared services (reference composition: Parties with EventStore, Tenants, Memories). Doubles belong only in isolated module tests, which run without Platform, execute first in CI, and never satisfy integration acceptance.
- **Run-scoped isolation:** Each suite or compatible batch gets a fresh run-owned environment with run-scoped ports, volumes, catalog instance, and isolated data (never staging/production). Conflicts fail fast naming the blocking run.
- **Readiness & startup bounds:** Wait for declared readiness checks and required startup tasks; a running process is not readiness, and missing readiness is a configuration error. Default startup deadline is **10 minutes** (excluding tests), overridable only by a justified finite declaration value. Record actual duration, effective deadline, override, and unready resources; raising a timeout is never faster startup.
- **Outcomes, retention & cleanup:** Record the first terminal outcome (`passed`, `failed`, `cancelled`, `withdrawn`) immediately and never overwrite it; `withdrawn` is neither pass nor failure and never evidence. Locally, success cleans up after holds end; any owner or attached test/startup failure retains surviving resources until explicit cleanup, even after later cancellation. Owner cancellation or explicit stop withdraws active attachments first without stopping separately started Aspire environments. Cleanup is idempotent, removes owned resources (not just metadata), reports leftovers, never claims completion with leftovers, and preserves redacted diagnostics and results.
- **Attachment & finite holds:** Explicit attachment requires a ready, compatible local or CI run-owned environment matching composition, mode, expected/loaded identities, readiness, and data isolation; refuse hosted targets, separately started Aspire environments, and finished owners unless failure-retained locally. CI attachment stays in the owner's same CI job. Holds start at acceptance, default to **1,800 s** when omitted, accept explicit whole seconds **1–14,400**, and reject invalid values (zero, negative, fractional, null, empty, malformed, non-finite, over-limit) without clamping or defaulting. Expiry is exclusive on the runner's UTC clock at immutable `expiresAt`, survives retries/reconnects, and stops attached work and access as `withdrawn` (reporting stopping failures without extending the hold). Cancelling an attached run ends only that run.
- **Disposable CI:** Run on disposable Linux GitHub-hosted runners with no staging/production credentials and only a read-only registry pull credential. Clean up after success, failure, cancellation, or partial startup, withdrawing attachments first. The always-run cleanup step and leftover report serve as the cleanup record, with runner disposal as backstop; no dedicated hosted scenario workflow is built.
- **Qualification & evidence:** Qualify on the reference composition across success, failure, startup timeout, cancellation, collision, owner finish/cancellation before attachment end, attached failure, hold expiry, and failure followed by cancellation, proving no other environment was touched. Bind each scenario to source revision, environment, result, actual startup duration, overrides, diagnostics, the released Builds catalog and SDK package lock, and observed Dapr CLI and `daprd` identities (or observed tools and stop point on partial startup). Keep evidence compact (summaries and CI links; no bulk logs/archives in git). Outside release CI, one retry of a non-reproducing failure is permitted while logging the flake as a bug.
- **Run-owned workload-binding authority:** Disposable runs needing bound workload tokens start a disposable Keycloak 26.6.4 with the provider over HTTPS via startup realm import only (no admin user/API calls), enrolling the exact consumer-derived inventory for that run's caller cohort and tenant for the run's lifetime. Write owner-only manifest/secret files in the run directory (`Folders:WorkloadEnrollment:ManifestPath`, `ManifestSha256`), use default TLS validation with process-launch trust (fail closed if missing, no bypass), refuse persistent/shared/hosted authorities and foreign-run manifests, clean up all created artifacts, and label evidence `run-owned enrollment` with no secrets, grants, or keys.

## Technical Decisions

- **Ownership & modes:** Platform owns the Aspire model, lifecycle contracts, and acceptance; Builds implements `hexalith-module` and reusable workflows. Fixtures read the descriptor and never start an AppHost; own-repository technical-module fixtures are never Platform evidence. No custom DSL or environment service is added. Local runs use active-root direct `references/` source in Debug (failing on nested submodules or duplicate identities, no fallback); CI uses Release, NuGet packages, and released images. The workspace tool manifest selects the local tool and alone controls mode; local and CI Dapr runtime, CLI, and .NET SDK versions come from the released Builds catalog.
- **Descriptor & result contract:** Versioned schema binding policy ID, contract versions, run/owner/CI/tool identities, composition/mode, endpoints, run-scoped catalog instance, synthetic tenant ID, expected/loaded artifact identities, candidate or `baseline-only` label, attachment lineage (`originalAttachmentRequestId`), hold timestamps, separate startup/execution deadlines, terminal outcome, termination observations, and leftovers. Unsupported versions fail naming supported versions; Epic 3 fields stay defined and marked unpopulated without qualifying evidence.
- **Candidate policy (`hexalith.platform.candidate-and-attachment-policy.v1`):** Merge gates test the committed merge result for the exact PR-head/base SHA pair (rechecked at merge; head-only evidence refused); release gates test the exact committed release revision. Every new decision requires a fresh run with no cross-decision reuse (even for unchanged modules or identical bytes); only the latest issued attempt for a pending gate-issued decision qualifies. Candidate evidence requires runner-owned package-mode CI on disposable runners completing a non-empty declared required test set; local and `baseline-only` runs are diagnostics only.
- **Tuple CI & released-version pins:** Platform tuple CI runs only source resolution and the current-tuple lane on the candidate commit behind a fail-closed verdict (no replay lanes, companion commits, or extra branches). The Builds binding holds only release version and tag (resolving to the Builds gitlink and matching `.config/dotnet-tools.json` and the range floor); AppHost and Tooling must match within `[pin, next major)` and pass lock verification. Owner packages verify against `eng/owner-packages.lock.json` (ID, version, hash) and loaded assemblies against archive members; CI restores in locked mode and fails before provisioning on mismatch. Composition holds no compiled release-identity literals, declaration-hash/image-digest allowlists, or measured cohorts; each test project declares one package profile. Adopting a new Builds or owner release requires only a version bump and regenerated locks while keeping expected/loaded identities in evidence.

## UX & Interaction Patterns

- Retained and pending-cleanup listings show owner, age, failed runs, attached runs, and absolute UTC hold deadlines.
- Refusals fail fast naming the blocking run, incompatibility, supported versions, or missing precondition.
