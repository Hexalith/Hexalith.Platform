## Findings and closure

### RR-01 — High, input preservation: migration sequencing omitted from the first draft — CLOSED

The first reviewed spine required supported Kubernetes before staging and Rancher at G1 but did not carry the source contract’s complete dependency order. The canonical migration spec’s Work order and Platform sequencing’s Around the gates require 4.26 qualification → 4.27 KubeSphere retirement → 4.1 supported native hop → 4.28 Rancher qualification → staging. Without that invariant, a builder following the mechanism authority could incorrectly install the manager first, wait for procurement before native maintenance, or postpone manager qualification until G1.

**Closure rechecked:** Cluster management now states the full order, refreshes post-retirement recovery inputs before the native hop, preserves every per-hop gate, requires initial manager restore before staging, and explicitly prevents procurement or Rancher availability from blocking native retirement/upgrade. Public administrative closure remains independently urgent. Release tiers now also distinguishes the pre-environment urgent procedure from later changes under environment locks, avoiding a dependency on machinery that does not yet exist. This preserves existing exact execution approvals rather than interpreting planning approval as live permission.

The vendor’s version-specific KubeSphere 4.2.1 guide lists Kubernetes 1.23.x–1.34.x, supporting retirement before the proposed 1.35 direction. Kubernetes lists 1.34 end of life as 2026-10-27 and 1.35.9 as the current 1.35 patch when checked. [KubeSphere 4.2.1 upgrade prerequisites](https://docs.kubesphere.com.cn/v4.2.1/03-installation-and-upgrade/03-upgrade-kubesphere/03-online-upgrade-kubephere-from-4.1.x/), [Kubernetes releases](https://kubernetes.io/releases/).

### RR-02 — High, input preservation/recoverability: management backup requirements too implicit — CLOSED

The initial Cluster management convention named recovery inputs and stale-authority fencing but did not explicitly preserve the canonical acceptance criteria’s management state/configuration, independently retained encryption configuration/keys, native management-cluster recovery, limited Rancher-app backup scope, or initial-versus-integrated proof timing. A generic reference to recoverable management state was thinner than these load-bearing source requirements.

**Closure rechecked:** The new Management recovery paragraph inventories Rancher application state/configuration, separate encryption material, TLS/registration inputs and native management-cluster recovery inputs under owners/recovery classes. It states that application backup does not restore downstream business data, workload external etcd or the complete management cluster. Initial 4.28 isolated restore/access proof precedes staging/G1; Epic 8 integrates management steps into existing cadence/retention, fencing/revocation and measured RPO/RTO gates. Existing workload recovery and the deputy’s authority boundaries remain binding.

This distinction matches upstream: the local-cluster operator backs up only Rancher application resources, and the backup tutorial explicitly says EncryptionConfiguration is not saved by the operator. [Rancher backup scope](https://ranchermanager.docs.rancher.com/how-to-guides/new-user-guides/backup-restore-and-disaster-recovery/), [Backing up Rancher](https://ranchermanager.docs.rancher.com/how-to-guides/new-user-guides/backup-restore-and-disaster-recovery/back-up-rancher).

### RR-03 — Low, qualification note: record the manager’s Helm tool identity — CLOSED

The approved owner-controlled Helm procedure has no selected tool version yet. Rancher’s v2.14 instructions and current installation guidance describe Helm v3; the existing application executor stack uses a Helm 4.2.0 floor. This is not evidence that Helm 4 cannot work, nor a request to reopen the application-tool decision. It means the existing application pin does not itself prove the new manager procedure is supported. [Rancher v2.14 Helm requirements](https://ranchermanager.docs.rancher.com/v2.14/getting-started/installation-and-upgrade/resources/helm-version-requirements), [Rancher installation procedure](https://ranchermanager.docs.rancher.com/getting-started/installation-and-upgrade/install-upgrade-on-a-kubernetes-cluster/).

**Closure rechecked:** Stack now explicitly treats the management installation Helm CLI and native recovery tools as separately qualified identities in the owner-controlled procedure, retaining the application-executor floor. Story 4.26 criterion 3, the migration spec and the qualification handoff carry the same distinction. The future runbook must record a compatible manager-installation identity or explicitly qualify Helm 4 reuse; this is ordinary execution evidence under the existing gate, not an unresolved architecture finding.
