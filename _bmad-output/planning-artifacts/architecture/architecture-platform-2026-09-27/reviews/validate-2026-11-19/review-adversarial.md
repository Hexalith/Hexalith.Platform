# Cross-team decision review

**Verdict.** The hosted release teams need a shared decision on when an admitted promotion can still be superseded. A separate mismatch changes which otherwise compatible maintenance releases can qualify for automatic promotion. Both findings concern the target design at commit `54d90be3`.

## High · Staging can supersede a release already rolling out in production

1. Candidate A passes staging. Production holds its lock, confirms A's pending decision, and starts deploying A. The previous working release still owns the latest-working pointer while A is being verified.
2. Staging independently acquires its own lock and starts candidate B. There is no Administrator reservation for A. A staging implementation that treats adoption as becoming the working baseline closes A's decision as superseded.
3. Production finishes A successfully and advances its latest-working pointer. The trusted gate must now record A's decision as completed. The same policy makes superseded decisions terminal. A second staging implementation could treat successful production admission as adoption and keep A's decision open. Neither the adoption instant nor a transition ordering shared by the two executors is specified. A production lock cannot serialize B's staging lock.

The difference affects which decision the release ledger records and whether B may trigger a staging reset while A is becoming the working baseline. The Story 5.1 review already identified this interval and assigned it to Stories 5.10 and 5.11. Their current acceptance criteria still use “has not been adopted” and require checking current evidence, without choosing the adoption instant. **Disposition — discuss before qualifying the two executors.** Platform and Builds should agree on the authoritative transition and its ordering against a later candidate's staging start. Qualify both orders and the admitted attempt's success and failure outcomes. The resulting baseline, promotion decision and reset eligibility must agree in each case. A change to fixed policy v1 semantics requires a new identifier and explicit adoption. ## Medium · A maintenance release has no candidate-new command for its rollback rehearsal

Consider a dependency-only release with unchanged operation declarations. The candidate can write valid state and events using an existing command, and the baseline can read them. A module owner following NFR-1 can supply that proof because the PRD and product acceptance criteria require a newly introduced idempotent command **where applicable**. The staging evaluator implementing policy v1 must demand a candidate-new command and refuse the compatible path when the required proof is missing. Story 5.8 repeats that unconditional rule. The two teams therefore reach opposite conclusions about the evidence required from the same release. [PRD line 349](../../../../prds/prd-platform-2026-09-27/prd.md#nfr-1-preserve-data-through-application-rollback) · [Product acceptance criteria line 174](../../../../../specs/spec-platform/acceptance-criteria.md) · [Spine line 315](../../ARCHITECTURE-SPINE.md#release-and-recovery-acceptance) · [Staging policy lines 313–331](../../../../../../docs/contracts/staging-evidence-policy-v1.md#serialization-and-preparation-branches) · [Story 5.8 line 3058](../../../../epics.md#story-58-rehearse-the-rollback-set-and-record-compatibility-evidence)

**Disposition — discuss before implementing Story 5.8.** The Platform Maintainer should decide whether a catalog with no new command may use an existing idempotent operation as the witness. If so, define how the suite proves that the candidate adds no operation and still exercises baseline readback, then version the fixed policy. If the gate intentionally requires a new operation for every automatic promotion, record that restriction in the PRD and product acceptance criteria. Qualify one candidate of each kind.
