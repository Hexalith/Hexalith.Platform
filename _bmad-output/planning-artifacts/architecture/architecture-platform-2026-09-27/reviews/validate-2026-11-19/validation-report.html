High findings

HighV1  ·  Correct implementation and requalify

Application deployment would own environment-managed Dapr Components

AD-8 gives the environment identity sole write access to every Dapr Component. The maintained application chart renders those objects, and the saved normal manifest contains eight. An application deployment using the prescribed permissions would be refused. Giving it those permissions would let application upgrades or rollback rewrite forward-only infrastructure bindings.

Action. Keep AD-8 as the ownership rule. Move Component rendering to the environment layer and qualify each application chart mode with the intended deployment permissions.

HighV2  ·  Align with adopted policy

Production promotion omits the adopted vulnerability gate

The spine’s production checklist can pass without scan evidence. Its handoff asks teams to choose a blocking severity. Platform already adopted a policy that blocks High, Critical and unresolved Unknown findings in both promotion modes, subject to a valid scoped exception. An otherwise passing release with an unexcepted High finding would receive opposite verdicts.

Action. Reference policy v1 in the common production preconditions. Give Story 5.5 responsibility for producing scan evidence and Story 5.11 responsibility for checking it at admission, including evidence age and exception state.

Production checklist L343 · Owned work L526 · Adopted thresholds L45 · Exception and execution responsibilities L68 · Scan evidence age L94

HighV3  ·  Align with adopted policy

An incompatible release can reach approval without the required restore rehearsal

The spine tells staging to prepare a rollback set whenever a production baseline exists. Its approved retained-data path asks the operator to name a recovery procedure. For that path, the adopted staging policy requires evidence of a rehearsed named restore and prohibits preparing an automatic rollback set. A written plan alone cannot prove recovery.

Action. Make staging select the applicable branch before qualification. For an approved retained-data release without valid compatibility evidence, require the full E2E pass and qualified restore, including authority, retained inputs, verification and treatment of post-cut changes. Retain the separate production post-lock recovery-point requirement.

Staging gate L315 · Approved release path L317 · Production precondition 9 L353 · Preparation branches L319 · Story 5.9 obligation L376

HighV4  ·  Align with adopted policy

A staging retry can start from data the candidate already changed

The spine describes a reset before a later candidate and identifies a point at the start of the unadopted candidate’s attempt. The policy also requires a verified reset before retrying the same candidate after unreadable or unproven writes. A later retry’s snapshot may already contain those writes.

Action. Apply the reset to both a later candidate and a retry of the same one. Retain and restore the earliest pre-write point for that candidate since the last verified reset. Require successful verification before the queued attempt starts.

HighV5  ·  Resolve an open design decision

Staging can supersede a release already admitted to production

Production checks that candidate A is pending while it holds its own lock. Before A becomes the working baseline, staging can start B and mark A superseded. If A then succeeds, the gate also has to close A as completed. The two executors have no agreed transition for this interval. The Story 5.1 review already recorded this open decision.

Action. Have the owners of Stories 5.10 and 5.11 agree when admission reserves a decision and which signed transition wins. Exercise B starting before admission, after admission but before completion, and after a failed production attempt. Follow the policy versioning rule for any change to adopted semantics.

Staging adoption L316 · Per-environment locks L320 · Admission check L58 · Terminal states L152 · Supersession rule L249 · Existing deferral L138

HighV6  ·  Correct the prerequisite

Module image attestations are scheduled after their first required use

The handoff makes owner image attestation due at first staging promotion. The publication workflow must already verify each module image’s attestation at intake. An unattested module therefore blocks publication even if its team meets the date given in the handoff.

Action. Move the owner attestation prerequisite to first admission for publication. Keep the check that refuses a missing or mismatched attestation before the release record is written.

MediumV7  ·  Correct the qualification sequence

Chart qualification asks for evidence that exists only after publication

The Aspire-to-Helm handoff bundles chart ownership, OCI attestation and retained-package rollback into one proof. Story 4.5 qualifies rendering and ownership before a published package exists. The epic assigns OCI evidence to publication and off-site package recovery to retention. Making all three part of the early proof creates a dependency on later work.

Action. Record the maintained-chart fallback. Split the handoff into chart qualification, verification of the published OCI attestation, and recovery of the retained package. Keep all three obligations at their owning gates.

MediumV8  ·  Resolve a requirement conflict

Dependency-only releases cannot supply a newly introduced command

The PRD asks the rollback rehearsal to exercise a candidate-new idempotent command where applicable. The spine, staging policy and Story 5.8 require one unconditionally. A dependency-only release can preserve the entire command catalog and still need a compatibility rehearsal.

Action. Decide what evidence proves that no command was added, and which existing command should demonstrate baseline readability in that case. Align NFR-1, Story 5.8 and the versioned staging contract before applying the decision.
