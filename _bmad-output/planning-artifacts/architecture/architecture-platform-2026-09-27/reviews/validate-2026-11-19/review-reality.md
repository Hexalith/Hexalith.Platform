# Reality check of the platform architecture

**19 November 2026 · Platform commit `54d90be3b661591048640d3585a8eab4aea0e534`**

**Verdict — changes required before the selected chart can qualify.** Its handling of Dapr Components conflicts with the platform’s deployment permissions and rollback contract. Two release-policy handoffs also disagree with decisions their owners have already recorded.

Paths and line numbers below refer to that commit and its pinned direct dependencies. “Spine” means `_bmad-output/planning-artifacts/architecture/architecture-platform-2026-09-27/ARCHITECTURE-SPINE.md`. This review compares design decisions, code, contracts and historical measurements. The only executed CI check was local source selection. Live infrastructure, package publication and external service availability were outside the review.

## Findings

1. **High — The application chart takes ownership of environment-layer Dapr Components.** AD-8 assigns Component writes to the environment-layer identity and withholds them from the application deploy identity. AD-3 requires a single owning tier. The release table assigns every Component to a forward-only environment change that precedes application rollout. The selected application chart creates a Component for each declared capability, including provider metadata, secret references and scopes. Its tests require each Component to appear. An application deployment using the mandated permissions will fail when it tries to manage these objects. Giving it the missing permissions would allow application upgrades and recovery renders to rewrite environment bindings. **Disposition:** enforce the existing boundary in the chart and its tests. Render the union of required Components in the environment step and verify that application and recovery renders only reference them. Requalify the reference chart. Evidence: Spine 94, 149, 278–285; `eng/helm-qualification/README.md` 9–20, 45–53; `eng/helm-qualification/chart/templates/dapr.yaml` 3–29; `eng/helm-qualification/test_chart.py` 351–356.

2. **High — The prerequisite table puts publication inputs at a later gate and downstream checks into chart qualification.** Spine 525 schedules module image attestation at first staging promotion. The publication workflow already has to verify each attestation before creating the release record. A team following the table could schedule its first publication without artifacts its publisher must require. Spine 519 also assigns OCI-attestation verification and retained-package rollback to Aspire-to-Helm qualification. Story 4.5 checks the package before publication exists. Epic 4 assigns OCI evidence to publication and off-site restoration to retention. **Disposition:** make module attestations an intake prerequisite to first publication. Keep deterministic rendering, admission and ownership in Story 4.5. Assign checks that consume a published or replicated digest to their publication and retention stories. Evidence: Spine 85, 240, 247, 519, 525; `_bmad-output/planning-artifacts/epics.md` 400, 686, 787–788, 2232–2235, 2295–2306, 2447–2449; `eng/helm-qualification/README.md` 153–160.

3. **High — The security policy handoff reopens an adopted release decision.** Spine 526 tells Builds and Platform to set the blocking severity and record exceptions. Story 5.2 has already adopted an immutable policy. High and Critical findings block, including unfixed findings. Unknown or unrated findings also block until the prescribed classification or an approved exception. Only Administrator can approve an exception, which expires after at most 30 days. The current handoff would let separate implementers pick conflicting thresholds or authorizers. **Disposition:** cite the adopted policy in the row and assign qualification of enforcement to Story 5.5. Evidence: Spine 526; `docs/contracts/image-and-dependency-vulnerability-policy-v1.md` 24–29, 45–65; `_bmad-output/planning-artifacts/epics.md` 2984–2996; `_bmad-output/implementation-artifacts/sprint-status.yaml` 193.

4. **Medium — Technology labels and the chart decision mix historical and current baselines.** The stack explicitly dates its seed to September but labels .NET 10.0.401 and Aspire 13.5.4 current. Today’s root selects .NET 11.0.100, Aspire 17.0.0 and toolkit 17.0.0-beta.1052. The pinned Builds catalog selects Dapr runtime 1.19.1. Separately, the Helm qualification used Aspire 13.6.4 and selected the maintained fallback after observing a missing sidecar annotation on all eight generated pod templates. This is a recorded design choice with open qualification. A reader reproducing the documented 13.5.4 setup would use neither the recorded Helm experiment nor the current application inputs. **Disposition:** point current pins to their owners. Date the seed and the Helm measurement explicitly, identify the maintained chart, and retain the open qualification requirement for changed inputs. Evidence: Spine 74–77, 384–396, 519; `global.json` 2–4; `apphost.cs` 2–10; `references/Hexalith.Builds/Props/Directory.Packages.props` 203–206; `eng/helm-qualification/README.md` 9–20; `eng/helm-qualification/toolchain.json` 14–20.
