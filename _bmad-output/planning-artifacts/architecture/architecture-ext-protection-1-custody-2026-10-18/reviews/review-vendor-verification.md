# Current vendor verification — EXT-PROTECTION-1 custody

Verified: 2026-10-18. Scope: the decision design and companion architecture spine. Primary AWS documentation only. No infrastructure, credentials, SDK calls, Live qualification or deliverable edits were performed.

**Verdict: suitable as a bounded feasibility proposal, with one evidence-retention clarification recommended. The cited vendor capabilities support the selected primitives; they do not establish the proposed composition, native transaction equivalence, installed availability or complete physical-copy qualification.** The design already labels those limitations honestly.

## Findings

### V1 — Medium: define the complete CloudTrail verification artifact

Sections 5/7 require retention of the native event and digest chain against separately retained trust, but do not spell out the non-body metadata that must survive a copy/export. CloudTrail places the digest signature in the S3 object's `x-amz-meta-signature` metadata. Validation also depends on the original S3 location, the regional signing public key selected by fingerprint and validity time, and the digest/log chain. A retained `.json.gz` file alone is insufficient. AWS's ordinary CLI validator expects original S3 locations; moved/offline artifacts need the documented custom validation path. Public keys for offline verification must first be retrieved online and retained securely. [Custom validation](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-custom-validation.html), [digest structure](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-validation-digest-file-structure.html), [CLI requirements](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-validation-cli.html).

Recommended correction: name an evidence bundle containing exact event/log/digest object bytes, source bucket/key/version identities, signature metadata, original-path binding, regional public-key bytes/fingerprint/time range, validation result and accepted trust revision. Retain that complete bundle under the same lifetime rule as the batch receipt. A copied digest without metadata or a missing/untrusted key remains Unknown. This is a refinement of the existing independent-trust requirement, not a new backend.

### V2 — Informational: native erasure and composition guarantees are correctly separated

AWS documents deletion of the KMS key and all associated HSM backing keys after the waiting period. It documents a distinct actual `DeleteKey` CloudTrail service event, including the affected ARN for events after December 2022. This supports observing the chosen logical key's permanent deletion; it is not a vendor-provided manifest certificate, customer-inspectable physical per-replica proof, or atomic KMS/DynamoDB commit. The design correctly leaves those stronger requirements unmet or subject to acceptance. Preserve that wording and the no-early-receipt rule. [Cryptographic deletion](https://docs.aws.amazon.com/kms/latest/cryptographic-details/key-deletion.html), [actual DeleteKey event](https://docs.aws.amazon.com/kms/latest/developerguide/ct-delete-key.html).

### V3 — Low: state explicitly that CloudTrail event order is not custody order

The proposal correctly obtains operation order from the DynamoDB head/hash chain. Add one explicit sentence preventing implementation from inferring native causal order from delivery order, array order, or timestamps alone: CloudTrail events do not appear in a guaranteed call order. Correlate the exact armed key/account/Region and event identity; use the durable custody intent for order. Missing evidence or logging/digest gaps must not become proof of absence. [CloudTrail concepts](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-concepts.html). Digest signing/validation proves integrity of delivered records; simply enabling validation does not perform validation. [Integrity validation](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-validation-intro.html).

## Capability check

| Claim checked | Current vendor support and interpretation |
| --- | --- |
| AWS-generated symmetric epoch | `CreateKey` defaults to `SYMMETRIC_DEFAULT`, `ENCRYPT_DECRYPT`, `AWS_KMS`. Plaintext symmetric key material does not leave KMS unencrypted. A 32-byte wrapping key fits its 4,096-byte encryption bound. Customer KMS keys are logical keys plus metadata. [CreateKey](https://docs.aws.amazon.com/kms/latest/APIReference/API_CreateKey.html). |
| Actual deletion versus scheduling/import deletion | Scheduling has a mandatory 7–30-day wait, potentially another 24 hours; PendingDeletion prohibits cryptographic use but is cancellable. Permanent deletion is irreversible. Deleting imported material is temporary: the same material can be reimported. The selected generated, single-Region key avoids the imported-material and replica exceptions. [Delete keys](https://docs.aws.amazon.com/kms/latest/developerguide/deleting-keys.html), [DeleteImportedKeyMaterial](https://docs.aws.amazon.com/kms/latest/APIReference/API_DeleteImportedKeyMaterial.html), [ImportKeyMaterial](https://docs.aws.amazon.com/kms/latest/APIReference/API_ImportKeyMaterial.html). |
| Survivor evacuation | `ReEncrypt` decrypts/re-encrypts within KMS and accepts native KMS ciphertext; it cannot process the existing outer AES-GCM wrapper. The design correctly applies it only to the KMS-encrypted wrapping key. Explicit immutable source/destination ARNs and exact contexts should be used; aliases are mutable. KMS is eventually consistent. [ReEncrypt](https://docs.aws.amazon.com/kms/latest/APIReference/API_ReEncrypt.html). |
| DynamoDB transaction bounds/retry | 100 actions, 4 MB aggregate, 400 KB per item; the same item cannot have separate ConditionCheck and Update actions. Put conditions on the head's Update itself. ClientRequestToken lasts ten minutes and does not promise byte-identical API responses. A small head/operation transaction plus permanent exact-outcome indexes is therefore a proposed application protocol, correctly separate from the service token. [TransactWriteItems](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TransactWriteItems.html). |
| Restored authority table | PITR/on-demand recovery creates a new table. Binding the live authority incarnation and rejecting restored-table self-promotion are application rules, not native anti-rollback guarantees. [Restore](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/pointintimerecovery_restores.html). |
| Immutable S3 versions | Compliance mode prevents alteration/deletion of a protected version during retention, including by the account root; it does not prevent new versions/delete markers. Exact version/hash selection and separate current-head ordering are required and present. Account survival remains a premise: vendor docs identify account deletion as an escape from compliance retention. [Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html). |
| CloudHSM backup rejection | AWS requires deleting old backups to avoid restoring deleted material; a requested backup deletion can be restored for seven days. The rejected ordinary-backup approach is accurately characterized. [Backup use](https://docs.aws.amazon.com/cloudhsm/latest/userguide/backups-using.html), [DeleteBackup](https://docs.aws.amazon.com/cloudhsm/latest/APIReference/API_DeleteBackup.html). |
| Cost illustrations | Current pricing examples support $1/key-month, $0.03/10,000 symmetric requests and $1.50 for 100,000 ECC-256 signing requests; scheduled-for-deletion storage is not charged. They remain examples, not a Paris quote or proof of the project's quotas. [Pricing](https://aws.amazon.com/kms/pricing/). |

## API versions

All four selected API date versions are supported by current primary references: KMS `2014-11-01` ([API PDF](https://docs.aws.amazon.com/kms/latest/APIReference/kms-api-reference.pdf)); DynamoDB `2012-08-10` ([history](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/DocumentHistory.html)); S3 `2006-03-01` ([API welcome](https://docs.aws.amazon.com/AmazonS3/latest/API/)); CloudTrail `2013-11-01` ([history](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-document-history.html)). The proposal accurately distinguishes API compatibility dates from a pinnable managed-service server release. None proves project access, quota or deployment availability.

## Remaining proof boundary

No inspected vendor document promises atomic arbitrary 1,000-target physical destruction with retained application receipts, complete closure of application plaintext holders, cross-owner governance/pin ordering, irreversible authority enrollment, or exact recovery of Platform's originals. Those are composition obligations. The offline model is a valid next implementation step, provided its report never promotes modeled guarantees to backend or Live evidence.
