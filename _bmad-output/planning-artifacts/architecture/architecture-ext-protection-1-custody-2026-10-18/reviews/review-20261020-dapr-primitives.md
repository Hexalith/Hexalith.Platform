# Dapr primitive and technology-floor review — 2026-10-20

Reviewed the current Platform checkout’s Dapr-only decision, custody spine, OWNER-APPROVAL.md and interaction-custody spec/contract/implementation plan. The earlier AWS proposal is historical input, not the reviewed adoption. This review used local source/public artifacts and primary Dapr/gRPC source or documentation only. It made no infrastructure/credential calls, deployment, component installation or destructive experiment.

## Verdict

**The Dapr output-binding extension is real and fits the proposed provider-neutral transport boundary. No built-in custody capability or installed component is fabricated. One transport-limit statement needs narrowing; one provisioning detail should be explicit.** Dapr abstraction does not establish physical erasure, independent authority, exact-original execution or transport-memory closure. The current documents correctly keep those as feasibility/qualification gates and forbid an application-native fallback.

## Findings

### DP-1 — Do not promise a deployment override for every message limit (P2)

Decision §Dapr contract, retries and authentication: “Configure sufficient bounded limits through deployment”; implementation plan I2.

The exact v1.18.1 pluggable output adapter invokes its generated client without a receive-size option. Its connector/discovery dialers do not supply a max-receive override. The pinned runtime uses grpc-go v1.80.0, whose documented default client receive ceiling is 4 MB. No ordinary deployment setting for raising this particular Dapr-to-pluggable-client ceiling was established by the inspected source. Increasing the public sidecar API limit or the custom component server’s limit does not by itself change that client.

Narrow the rule to: configure the limits that the selected runtime actually exposes, and require the largest legal request **and response**, including protobuf/envelope overhead, to fit every remaining fixed ceiling. F1 must stop if it cannot fit. Do not infer a knob, split a manifest or add an application-native path; any runtime/component change must be supported, independently pinned and explicitly qualified.

Sources: [v1.18.1 output adapter](https://raw.githubusercontent.com/dapr/dapr/v1.18.1/pkg/components/bindings/output_pluggable.go), [connector](https://raw.githubusercontent.com/dapr/dapr/v1.18.1/pkg/components/pluggable/grpc.go), [discovery](https://raw.githubusercontent.com/dapr/dapr/v1.18.1/pkg/components/pluggable/discovery.go), [runtime dependency version](https://raw.githubusercontent.com/dapr/dapr/v1.18.1/go.mod), [grpc-go receive-size default](https://raw.githubusercontent.com/grpc/grpc-go/v1.80.0/rpc_util.go).

### DP-2 — Freeze reflection, socket identity and imported proto requirements (P3)

Decision §Verified evidence and Dapr capabilities / §Exact stack; binding contract and implementation plan I2.

The retained binding proto is correct, but implementing its four RPCs alone is insufficient for Dapr’s automatic registration. The component must expose gRPC reflection, start before sidecar discovery and share an accessible UDS. Type naming is derived from the socket basename: proposed `bindings.hexalithcustody` requires the corresponding `hexalithcustody` socket identity, while the configured binding instance name is a separate value. Proto code generation also needs the exact-tag imported `common.proto` and its dependencies.

Add these to I2’s artifact/provisioning checklist rather than leaving implementers to infer them. Pin generated protocol inputs; require Init/ListOperations/Ping and discovery/initialization failure tests. This is a supported setup requirement, not evidence that the new component exists.

Sources: [registration and naming](https://docs.dapr.io/operations/components/pluggable-components-registration/), [implementation requirements](https://docs.dapr.io/developing-applications/develop-components/pluggable-components/develop-pluggable/), [exact binding proto](https://raw.githubusercontent.com/dapr/dapr/v1.18.1/dapr/proto/components/v1/bindings.proto).

## Verified floor and limits

- **Exact retained protocol:** independently fetched the v1.18.1 `bindings.proto` and compared its bytes with `dapr-bindings-v1.18.1.proto`. They match; SHA-256 is `cccf28040eedce15edd44c7bc0589b232ed28dd40de40f205d69f93edb663d5d`, matching the research record. `dapr.proto.components.v1.OutputBinding` has Init, Invoke, ListOperations and Ping. Invoke carries bytes, string metadata and an operation; its response carries bytes, metadata and content type. These are supported transport fields, not lifecycle semantics. [Exact proto](https://raw.githubusercontent.com/dapr/dapr/v1.18.1/dapr/proto/components/v1/bindings.proto).
- **Custom operations:** v1.18.1 obtains the operation strings from ListOperations and admits only an advertised operation. Therefore the proposed semantic allowlist can be implemented by a custom binding. Dapr does not predefine `destroy-manifest`, `lookup-original` or their guarantees. The architecture correctly calls `bindings.hexalithcustody` proposed, absent and unqualified. [Operation admission](https://raw.githubusercontent.com/dapr/dapr/v1.18.1/pkg/runtime/processor/binding/send.go).
- **Public API:** HTTP `/v1.0/bindings/<name>` and the corresponding Dapr gRPC invocation API are supported. Component `spec.version: v1`, public binding API `v1.0`, and the application semantic version `custody-lifecycle-v1` name different layers; the documents keep that distinction. [Bindings API](https://docs.dapr.io/reference/api/bindings_api/).
- **Existing .NET dependencies:** current `references/Hexalith.Builds/Props/Directory.Packages.props` and sibling Builds both pin Dapr.Client and Dapr.Actors to 1.18.10; Platform imports that catalog and its custody project already references those packages. The exact v1.18.10 SDK source contains the required InvokeBinding overloads. This verifies source/API availability, not a successful new service build. Builds’ separate default runtime property is 1.18.2; observed installed runtime 1.18.1 is correctly identified as an observation, and actual qualification must pin the complete runtime/SDK/component combination. [SDK declaration](https://raw.githubusercontent.com/dapr/dotnet-sdk/v1.18.10/src/Dapr.Client/DaprClient.cs).
- **Retry behavior:** v1.18.1 applies `ComponentOutboundPolicy` around each binding invocation. A custom resiliency policy may repeat it. Zero configured retries does not establish exactly-once delivery, permanent idempotency, native-request cancellation or absence of late effects. The component’s durable original/intents and Unknown rules remain necessary, as stated. [Binding call path](https://raw.githubusercontent.com/dapr/dapr/v1.18.1/pkg/runtime/processor/binding/send.go), [retry policies](https://docs.dapr.io/operations/resiliency/policies/retries/retries-overview/).
- **SDK memory copies are a concrete feasibility concern:** v1.18.10 generic binding calls serialize to a temporary UTF-8 array and copy it into protobuf ByteString. The raw BindingRequest overload also uses ByteString.CopyFrom and returns response ByteString memory. The inspected paths do not explicitly zero those temporary/protobuf buffers. Thus normal owned application-buffer disposal cannot qualify all-copy erasure. The current requirement to prove SDK/sidecar/component completion or accepted termination, otherwise stop, is appropriate and must remain a gate. [SDK invocation implementation](https://raw.githubusercontent.com/dapr/dotnet-sdk/v1.18.10/src/Dapr.Client/DaprClientGrpc.cs), [serialization conversion](https://raw.githubusercontent.com/dapr/dotnet-sdk/v1.18.10/src/Dapr.Client/TypeConverters.cs).
- **UDS is a local trust boundary:** the exact connector uses insecure gRPC credentials over a Unix socket; this hop does not acquire remote Dapr mTLS identity. Filesystem/socket permissions, process identity and independently verified operation proofs are required. The documents correctly deny authority based on binding name, metadata, app ID or mTLS alone. A colocated process is not an independent failure domain. [Connector](https://raw.githubusercontent.com/dapr/dapr/v1.18.1/pkg/components/pluggable/grpc.go).
- **Built-in crypto is not lifecycle custody:** the documented crypto components/engine expose cryptographic operations and an opinionated Dapr Crypto Scheme, not this complete manifest/hold/current-authority/original-result contract. The document correctly rejects substitution of generic state/secret/crypto calls and preserves the existing AES-GCM/AAD/envelope contracts. No complete supported built-in provider was established. [Crypto inventory](https://docs.dapr.io/reference/components-reference/supported-cryptography/), [crypto overview](https://docs.dapr.io/developing-applications/building-blocks/cryptography/cryptography-overview/).

## Infrastructure independence and approval reconciliation

The latest owner constraint is reflected consistently in the decision, spine AD-25, approval disposition and spec: application code and configuration use Dapr plus neutral custody identities/proofs; native SDKs, resource IDs and credentials belong only to a replaceable infrastructure component. The direct Platform AWS adapter, mandatory AWS accounts/Region and AD-9 exception are explicitly superseded. Historical AWS SDK pins and the retained provider profile are research inputs only. Parent AD-9 is not rewritten.

The new deployment/recovery classes remain explicit and independent of the application restore/failure domain. The UDS-facing component alone supplies no independence; actual backing authority/evidence placement remains an installation input. OpenBao’s observed ordinary-Raft revival remains disqualifying under Dapr too. No successful binding call is described as physical qualification or Available.

The transport floor is therefore plausible for I1/I2 investigation, conditional on DP-1 and the existing memory/physical/provider gates. This review establishes no component artifact, provider choice, cloud entitlement, current trust installation, secret cleanup, maximum-vector result, erasure or owner-cohort result.

## Follow-up closure — corrected decision and binding contract

Re-read the corrected current decision and `custody-binding-contract.md` after the author's fixes. **DP-1 is closed at the documentation level:** the fixed 4 MiB pluggable-client response ceiling is explicit; no runtime configuration override is inferred. Complete input manifests remain one invocation, and F1 must prove their worst legal request encoding fits the supported SDK/sidecar/component limits or stop for an explicitly approved supported revision. No implicit public-field restriction or partial admission is allowed.

Large immutable value-free results now use a bounded authenticated OriginalResultReference header and read-only `read-original-page` operations: at most 256 KiB original bytes per page and a wire frame below 1 MiB. Complete contiguous assembly and total identity/hash/vector/signature verification precede public Consumed. Interrupted assembly remains Unknown; no key payload is paged or cached. This frames one selected immutable result; it does not partition target admission, native effects or the original terminal vector. The new operation fits the verified arbitrary advertised-operation surface. Actual maximum-size and timing conformance remain F1/F2/F3 work, not a result of this review.

**DP-2 is closed at the documentation level:** the decision and binding contract require pinned imported protos, gRPC reflection, socket/type discovery matching, restrictive UDS mounts/ownership and immutable enrolled Init conformance. Re-registration cannot clear originals, native intents or uncertain holders, and changed authority/profile cannot enter through Init. No code generation, component registration or installed compatibility was claimed or tested.

No remaining unsupported transport primitive was identified in these fixes. The implemented component/provider, complete sidecar/SDK/key-memory closure and physical independently observed erasure remain explicitly absent and blocking; neither closure finding establishes qualification.
